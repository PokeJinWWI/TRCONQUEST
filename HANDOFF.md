## Decisions
- **Outliner selection lifted to `viewStore.inViewSelection`** (a scene-local id/name, meaning differs per scene: star id in interstellar, body/moon name in system/satellite) so the sidebar can drive what each scene has selected, mirroring exactly what clicking the in-scene marker does (including engaging that scene's `SelectionTracker` camera lock). Fleet entries drive `shipStore.selectedShipId` the same way.
- **Fleet allegiance** (`player`/`friendly`/`neutral`/`hostile`) lives on `ShipInstance`, not `ShipClass` — a hull doesn't imply who's flying it. `ALLEGIANCE_COLORS` (`shipData.ts`) is the single source every fleet-colored element reads from (viewport triangles, Outliner icons, interstellar presence badges). `DebugConsole` has an allegiance selector (default `player`) since nothing else assigns allegiance yet.
- **Ownership gates *commanding*, not *selecting*.** First pass wrongly blocked selection itself; corrected — `shipStore.selectShip` always allows any id (so players can inspect enemy/neutral/friendly fleets), while `shipPhysics.planMove` is the single chokepoint refusing to *plan a move* for a non-player ship (`{kind:'not-owned'}`). `ShipPanel` shows "Not under your command." instead of the redirect hint for a selected-but-unowned ship.
- **Interstellar presence badges**: small, deliberately no-text triangle icons next to a star's marker when a fleet is nested inside that system (e.g. orbiting a planet) and thus has no interstellar-scale position of its own. One per distinct allegiance color present (`fleetPresenceByStar: Map<string, ShipInstance[]>`), clickable to select the ship they represent (`e.stopPropagation()` so it doesn't also select the star).
- **A resting, orbiting ship shows no name label** (Stellaris-style, just the triangle) — `ShipMarker`'s `isOrbiting` gate; `SatelliteShipMarker` never shows one, since every ship it renders is orbiting by construction. A travelling ship, or one resting at a bare star/point, keeps its label.
- **Ships resting in orbit have real, continuous orbital motion**, not a static parking spot, in *both* system view and satellite view, sharing the same underlying angular motion. `ShipLocation`'s `'orbiting'` variant stores only `periodDays`/`phaseDeg` (genuine time-basis state) — the *radius* is a per-view rendering constant (`SYSTEM_SHIP_ORBIT_RADIUS = 0.15` scene units vs. satellite view's pre-existing `primaryVisualRadius + 1.2`), since real planet radii are near sub-pixel at true AU scale and an orbit radius was never a literal distance to begin with (same reasoning as `MOON_TIME_DILATION`). Reuses `orbitMath.ts`'s existing `getOrbitPosition`/`angleForYear` — no new circular-motion math. Default period `DEFAULT_SHIP_ORBIT_PERIOD_DAYS = 4`.
- **Ship-to-marker overlap fixed at the screen-space layer, not world-space.** A world-space nudge (`restingOffset`, 0.6 scene units) shrinks to ~1px on screen at any reasonably zoomed-out camera distance — exactly when overlap is most visible. Real fix: `.ship-marker { transform: translate(4px, -18px) }`, a CSS screen-space offset guaranteeing separation at *any* zoom. Kept `restingOffset` too (still useful up close, spreads multiple ships apart) — the two aren't in conflict, just different scales.
- **Cross-system move-order distance bug fixed**: a ship resting in interstellar space ordered to a body in a *different* system used to have its start position collapse to that system's own origin, silently discarding the interstellar leg it needed to make first. Fixed via a symmetric `interstellarAnchor(info)` applied to both ends of a cross-space order.
- **Satellite view never had right-click-to-order wired up at all** — real gap, now fixed (`onOrderTo` prop added to `FocusableMarker` and `HologramBody`, targeting the scene's own `bodyName`).
- **Order settlement (clearing `ship.order`, applying the resting location) moved out of `ShipMarker`'s per-instance `useFrame` into a new global `useShipOrderSettler` hook**, mounted once in `App.tsx` outside any Canvas (same reasoning as the pre-existing `useGameClock`) — subscribes to `useGameTimeStore` rather than running its own rAF loop. Fixes a real, easily-hit gap: an order completing while the player is in a view that doesn't mount that ship's marker (e.g. satellite view, now that it can issue orders) used to never settle.
- **Found and fixed the root cause of two separately-reported bugs** ("Go To" jumping into a stale body's satellite view after arriving; ships "stuck in arriving" when ordered to a star system from interstellar view): every scene's "zoom in close enough → auto-enter next view" `DistanceThresholdWatcher` only checked a *stale* body/star/moon selection, never whether a ship was *also* currently selected — selecting a ship deliberately never clears that other selection (correct, separate design). Fixed by adding `!selectedShipId` to all three watchers (`SolarSystemScene`, `InterstellarScene`, `SatelliteViewScene`). Verified live: reproduced the exact stale-selection setup and confirmed no more unwanted navigation, with the underlying settle mechanism independently confirmed to have never been broken.
- **Warp drives have a 5-day cooldown (`WarpDrive.cooldownDays`, mirrors `HyperDrive`'s shape) but never block an order** — on cooldown, the trip just uses reaction-drive speed instead (`MoveOrder.usedWarp` records which applied, read once at arrival by `warpCooldownAfterArrival`). Hyperdrive cooldown *does* block outright (no other way to cross interstellar distance fast) — but now supports **"jump when ready"**: ordering a hyperdrive jump while on cooldown queues it (`ShipInstance.pendingHyperdriveJump`) instead of silently dropping, firing automatically via `useShipOrderSettler` once ready.
- **`ShipPanel` shows a "Cooldowns" row** (`Hyperdrive Xd` / `Warp Xd` / `Ready`) for whichever drives the ship's class has, plus an ETA on the status line while travelling (shared `formatDate`, moved from `TimeControls.tsx` into `gameTimeStore.ts`) and a **"Go To" button** — reuses `CameraFocusRig` exactly like planet/star fly-ins, but `onArrive` does nothing view-level (a ship has no deeper view to enter); independent of the `lockOnEnabled` toggle (one-time fly vs. continuous follow). Gated on each scene's own `trackedShip` (only present when the ship is actually there to fly to).
- **Lock-on toggle** (top HUD, `viewStore.lockOnEnabled`, default on) gates the *continuous-follow* part of every scene's `SelectionTracker`; the no-selection default-anchor behavior (what exit-via-zoom-out measures against) stays active regardless, since that's navigation plumbing, not "following a selection."
- **Moons render an actual `HologramBody`** (not just a marker dot) in satellite view, sized to `moon.visualRadius` — a moon like Luna (a quarter of Earth's size) was understating itself as a bare dot. Paired with `MAX_ORBIT_RADIUS = 12` clamp in `moonData.ts` so far-out moons stay within the default camera framing.
- **Initial/fresh-arrival system-view camera (`FAR_START`) brought ~4.4x closer** — the old distance was tuned for how *leaving* felt (a "shrink to a dot" effect on exit), which doubled as an illegible *entry* framing.
- **NavBar/Outliner collapse-toggle had two real, separate CSS bugs**, both fixed: (1) a transition-timing garble (long labels visibly clip to single characters mid-animation — fixed with an asymmetric opacity transition, instant fade-out / delayed fade-in), and (2) a persistent *resting*-state bug where the content div's padding never actually shrinks to 0 under `flex-basis: 0%`, overflowing the collapsed 28px container and clipping the toggle arrow itself on the left-anchored `NavBar` (padding now explicitly zeroed in the collapsed state on both sidebars).

## Constraints
- **No backend** — pure client-side app; "dev-only" only ever means "stripped from the production bundle by Vite's dead-code elimination," not truly secret.
- **No real gameplay/economy/tech-tree systems** — habitability, districts, drive tiers, etc. are real *data* with heuristics/placeholders, documented throughout `Context.md`, not a gap to silently paper over.
- **`npx tsc --noEmit` does NOT actually typecheck this project** — `tsconfig.json` is a solution-style file (`files: []`, only `references`), so that command silently checks nothing. Use **`npx tsc -b`** (matches what `npm run build` actually runs) for real verification.
- **No eslint installed** (not a devDependency; `npx eslint` fails via network) — don't attempt lint checks.
- **Sandboxed browser testing, several distinct issues found this session, all environmental (not app bugs)**:
  - `document.hidden`/no focus suspends `requestAnimationFrame` *and* visibly delays React's own re-renders — a store write can be correct immediately while the DOM takes ~1-3s to catch up. Don't conclude "broken" from an immediate re-check; wait and recheck.
  - **Real wall-clock time keeps advancing for the live page during agent reasoning between tool calls, not just during explicit `wait()` calls** — caused real confusion this session testing time-based cooldowns; always re-read the in-game date to sanity-check elapsed time rather than assuming only explicit waits counted. Pausing the in-game clock is the reliable way to get precise timing control for tests.
  - The 2nd+ `<Canvas>` mount within one browser-pane tab can lose its WebGL context deterministically (breaks all rendering, including `Html`-portaled DOM). Open a **fresh tab** for each new view-level transition being tested rather than navigating repeatedly in one tab.
  - **Dynamic `import()` of a *stateful* module (a zustand store) in the browser pane is unreliable** — sometimes returns a disconnected module instance with empty/default state, especially after recent HMR churn. Pure-function modules (`shipPhysics.ts`) are safe and were used extensively for precise testing. For anything stateful, drive the real UI (clicks, `dispatchEvent`) instead of poking the store directly.
- **Filesystem is case-insensitive** (macOS) — `CONTEXT.md`/`Context.md` are the same file. Session handoffs go in `HANDOFF.md` instead, per this project's own established precedent (do not write a `/newchat`-style handoff to `CONTEXT.md`/`Context.md` — it would silently overwrite the real project doc).
