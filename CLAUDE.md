# Terra Relicta: Conquest

Web grand-strategy game: Vite + React + TypeScript + three.js/r3f, zustand stores. Two-person team. The user here is mr1noobfatfish, the author of Complex economy mode (`src/economy/*`) — treat it as the user's own code.

## Standing rules
- **Never commit unless explicitly asked.**
- **Verification sweep after any change:** `npx tsc -b`, every `tests/*.test.ts` (`npx tsx tests/<name>.test.ts`), and `npm run build`. All must be clean.
- **Filesystem is case-insensitive.** `Context.md` (~330KB, git-tracked running log) is the same file as `CONTEXT.md`/`context.md` — never overwrite it or create a differently-cased "separate" file. `HANDOFF.md` is a separate, older handoff note (partly stale).
- Don't read `Context.md` whole — grep it for the section you need, or read with offset/limit.
- Dev server serves from `/TRCONQUEST/`. Onboarding gate: pick a nation first (`usePlayerStore.getState().selectCountry(id)`; ids: `imperial-state-of-mars`, `republic-of-venus`, `orion-republic`, `kingdom-of-lalande`).

## Terminology
- **INTERSTELLAR** = travel between stars within one cluster (interstellar view). **INTERCLUSTER** = travel between clusters (galactic view). Never conflate.
- **Slips** = the Shipyard's build-slot subtab (not "Ships").
- **Warp Mk I to VII** = warp drive research levels (`data/warpData.ts`).
- **Standard sweep** = `npx tsc -b`, every `tests/*.test.ts` via `npx tsx`, and `npm run build`.

## Verification conventions
- **Store-probe:** to test UI state fast, temporarily expose zustand stores on `window` from `src/main.tsx`, drive them via the browser JS tool, and **always revert `main.tsx`** before ending the turn.
- Browser pane can be "hidden" (rAF suspended, stale `getComputedStyle`); verify via DOM attributes / screenshots, and use `setTimeout` not rAF for guaranteed callbacks. Vite HMR sometimes reloads to the onboarding screen — just redo setup.
- Tests are plain `tsx` scripts with a local `check()` helper, not a framework. One file per feature area; add a test file for any new mechanic and regression tests for bugs found.

## Architecture notes
- Pure-function resolvers separate from store I/O (e.g. `stepEngagements` in `scene/combatResolution.ts` vs `hooks/useCombatResolver.ts`). Keep new logic pure and testable.
- Timers are absolute `simDays` deadlines, never countdowns.
- Data/balance constants live in `src/data/*` (`combatData.ts`, `shipModules.ts`, `techData.ts`, `commsData.ts`); state in `src/state/*`.
- Optional new fields on `ShipInstance`/`CombatParticipant` default via `??` so existing literals and tests don't need updating.
- Zustand selectors should return primitives (join ids into a string) to avoid re-render churn.
- **FTL comms** (`scene/commsVisual.ts`): simulation state is live truth, and every ship is DRAWN at its real position (`playerShipRenderPosition`); there is no "predicted" marker. Panels, health bars, status text and route lines are LIVE (the delayed `visualShipSnapshot` is no longer used by any view); what lags is signal time: orders and ship commands queue behind it (`queueMoveOrder`/`queueStance`, `scene/shipCommands.queueShipCommand`; fired by `hooks/useCommsResolver.ts`), and a fight is unknown until its news arrives (`engagementKnownToPlayer`: not in the battle list, no Enter Combat, no auto-pace to TAC). Delay is computed from the ship's *live* position (`playerCommsDelayToShip`), never stale `ship.location`. Combat arena stays live. Hyper Comms = zero delay everywhere. **The AI obeys the same delay:** every order to a ship (`queueFleetMoveOrder`, `queueShipCommand`, `queueBombard`) is a signal from the ship OWNER's capital at the owner's own comms tier (`ownerCommsDelayToShip`; direct-contact arena exemption is for the player's ships only; nations with no capital, i.e. sandbox factions, have none), applied on arrival by `resolveCommsSignals` (`hooks/useCommsResolver.ts`, exported so headless tests drive it) with `plannerFor(ship)` (gated for the player, unchecked for AI). The AI reads its `known` survey layer (reports take signal time), treats a ship with an order/command in flight as busy (`ai/blackboard.hasOrderInFlight`, else a resend would restart the signal clock forever), and every nation STARTS with Hyper Comms (`techStore.DEFAULT_RESEARCHED`, via `startingCommsTech(drives)`: a hyperdrive nation gets Hyper Comms = zero delay, Warp Comms would only be the default of one that also starts with a warp drive; Warp Comms needs Warp Theory + Quantum Mechanics and costs `WARP_COMMS_EXOTIC_COST` exotic matter and is NOT on `AI_RESEARCH_PATH`; every prerequisite of a starting tech also starts researched), so signal delay is only a tier tests set explicitly (`tests/testComms.warpCommsOnly()` puts the four nations on Warp Comms; `ai.test.ts` is pinned to it: on Hyper Comms the AI's builder never gets a charted lane out of Sol under its 5% jump cap, so `colonies.test.ts` section 8 currently fails, known). It still reads its OWN ships' live state (position, cargo) — only orders and discovery reports are delayed.

- **Orbital combat & Free Flight** (`scene/freeFlight.ts` pure, `combatArena.orbitPrimary` / `hasSignificantGravity`, `combatResolution.integrateMotion`'s `canFreeFloat`, `scene/ShipFreeFlightToggle.tsx`; `tests/freeFlight.test.ts`, `combat.test.ts` 60-62): a ship has free flight when its OWNER has researched `free-flight-maneuvering` (nobody starts with it; it is on `AI_RESEARCH_PATH` before Hyperdrive Mk II) AND its own `ShipInstance.freeFlight` is not off (absent = on, so on by default once researched): `freeFlightActive`, read per ship by `resolveSpaceCombat` for every nation, AI included (no AI-specific code; the AI never switches it off). An idle ship is NOT pulled on top of its orbit hold. A dead drive falls at the full pull as before (`gravitationalAcceleration` now sums significant bodies only). Buildings: click a queued tile to stop it; the picker builds 1/3/5/fill at once. **Deconstruction** (building or district level) is a `Teardown` (`AbstractEconomyState.teardowns`, `queueDemolish`/`queueDemolishDistrict`, `cancelOrder` stops either): its own bar that runs DOWN from the build cost over `DECONSTRUCT_MONTHS_*` on its own clock — no construction points, no queue place, no slot — and the thing is removed at 0 (a district level only if its buildings still fit). **`DraggableWindow` resize:** 8 handles (`RESIZE_HANDLES`), the edge opposite the dragged one stays put (pos shift = half the ACTUAL size change, whole for edge-anchored windows; clamps equal the CSS max-width/height); the height `ResizeObserver` ignores windows with an explicit size (it used to re-shift a window after the pointer was released). Same-nation border bubbles near each other are joined (`TerritoryDiscs` LINK_*). **Vassalization** is a peace term (`{kind:'vassalize'}`, `VASSALIZE_SCORE` 70, halved when exhausted): ends the war and makes the loser a subject (`makePeace`); refused against an existing subject. No casus belli system.
- **Tooltips & charts:** hover tooltips are global (`components/TooltipLayer.tsx`, mounted in `main.tsx`) — give any control a `title` and it gets a styled tooltip (the ONE tooltip system: the layer lifts EVERY title up the tree while hovered (`titledChain`, not just the nearest — else the browser falls back to an ancestor's plain tooltip a moment later) and re-lifts one a re-render puts back (MutationObserver); in SVG use `data-tooltip`, never a `<title>` child); add concept explanations to `data/glossary.ts` (short labels matching a term get them automatically, in both modes). History graphs use `components/TimeChart.tsx` (month x axis, value y axis, 6M/1Y/3Y) with `endTick` = the economy store's tick.
- **Time & interruptions:** three paces on one clock (`gameTimeStore`): STRAT 6 d/s, OPS 1 d/s (ground battles), TAC 1 s/s (ship combat), picked directly from three buttons. Fights the player is in auto-switch the pace only when they START (`useCombatResolver`, `useGroundCombatResolver.followGroundFightWithClock`), never while one is going on, so the player can always switch back. AI peace offers to the player pause the game (`confirmStore` `pausesGame`) and are throttled with a per-war cooldown that doubles on each decline (`ai/executor.mayOfferPeaceToPlayer`). The Outliner's Battles section (`scene/battleList.ts`, kept current in `state/battleStore.ts` by `hooks/useBattleTracker.ts`) lists every space and ground battle the player is in and opens it, and `components/BattleBadge.tsx` marks the same fights on every map level (body, star and neighbourhood markers). The pace only ever moves DOWN on its own (`hooks/fightPace.ts`): a ground fight takes STRAT to OPS, a space fight takes STRAT or OPS to TAC, a ground fight never pulls TAC up, and a space fight ending mid ground battle lands on OPS. When the last fight ends (ground fights count 2 sim-days after the last shot; a space fight ends when no hostile pair is left, even though its engagement stays open holding the victor, `resolveSpaceCombat` in `hooks/useCombatResolver.ts`, tested headlessly in `tests/pacing.test.ts`) the clock returns to STRAT whatever pace it was on; a pace the player picks with no fight going is left alone. The cheat console (`DebugConsole`, backtick or the Sandbox panel's button, open state in `state/debugConsoleStore.ts`) is mounted in dev builds and in the sandbox in ANY build, so it ships in production but only renders in the sandbox. Moons are treated like planets for panels and the Outliner (tabbed inspect panel, Colonies list, own Armies row). **Moons are real destinations:** a ship orbits a moon as `{kind:'orbiting', bodyName:<moon>}` (its own orbital superiority, blockade, invasion, patrol, combat arena); at system scale `shipPhysics.bodyLivePosition` puts a moon on its planet (`moonParent`), so travel and the system-view marker are the planet's, and the satellite view draws the ship circling the moon (`satelliteShipLocalPosition`); right-click a moon there to move to it.

## Performance rules (lag has come from these before)
- **Never subscribe a scene or a big component to `simDays`** (`useGameTimeStore((s) => s.simDays)`): it re-renders the whole tree on every frame (a map with 300+ Html markers was unplayable). A scene that needs Starbase claims uses `hooks/useStarbaseActivity.useStarbaseActivityKey` (changes only when a Starbase finishes) and reads the clock with `getState()` inside the memo; a panel that only displays the clock uses `hooks/useThrottledSimDays` (≤4 renders/s).
- **Many markers = one point cloud, not one DOM element each.** The galaxy view's 321 neighbourhoods are `scene/GalaxyMarkers.tsx` (a ring texture on `<points>` in three layers: dots, claim rings, hover/selection highlight; picking by screen distance in pure `scene/galaxyPick.ts`, done from the click handlers; only hovered/selected ones get an `Html` label and only ones with a fight get a battle badge). 321 drei `Html` overlays repositioned every camera frame is what made it lose fps. Do the same for any view that grows past a few dozen markers.
- Per-frame code (`useFrame`) must be linear in the number of things on screen: compute shared per-frame data once (e.g. `GroundViewScene.fanOf`), never rescan every unit from inside each unit's marker.
- The browser pane throttles `requestAnimationFrame` to ~1 fps once a WebGL canvas is up, so it can't measure frame rate; find lag by reading for the two patterns above, and benchmark the pure sim in Node.
