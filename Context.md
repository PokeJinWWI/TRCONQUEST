TR: Conquest
# Overview:
"Terra Relicta: Conquest" is a web-based grand strategy game.

# Setting / Lore:
## FTL Travel
Two methods of faster-than-light travel exist:
- **Warp Drive** — uses "Exotic Matter," a form of matter found on certain planets with a higher mass-energy conversion rate than normal matter. Warp drives use exotic matter to warp and move space itself to travel.
- **Hyperdrive** — uses "Hyperium," extremely rare to find naturally but yields effectively infinite energy. Hyperium cannot be broken up/subdivided, so each ship equipped with a hyperdrive is extremely valuable. Hyperdrives use hyperium to access "hyperspace," a dimension outside the normal universe where time passes faster, allowing FTL travel. (Exact mechanics of hyperspace aren't important to nail down yet.)
- Both exotic matter and hyperium don't just power FTL drives — they also power the entire ship's systems and weapons.

## STL (sub-light) Travel
- STL warp drives tend to use **antimatter**, harvested via massive particle accelerators or extracted from locations with high "antimatter density."

## Timeline
- The game's campaign starts in the **year 2600**.

# Visual Style / UX Reference:
- The game should look like a tactical map, similar to **DEFCON** (see reference screenshots: minimalist neon vector map, arcs for missile/unit trajectories, glowing markers, DEFCON-style HUD/side panels).
- Scale/view structure (4 zoom levels, see View Levels below):
  - **Satellite view** (internal `level: 'satellite'`, was called "planet view" — renamed since it now also handles stars and, eventually, other close-up-inspectable things like asteroids/black holes): close-up of a single planet or star, with any of its moons.
  - **System view**: 2D-ish top-down (like DEFCON's flat world map).
  - **Interstellar view**: 3D, styled like an **Obsidian graph view** — nodes (nearby stars) connected by edges.
  - **Galactic view**: 3D, same graph style, zoomed out to galaxy scale (placeholder only so far).

# Tech Stack:
- **Vite + React + TypeScript** (scaffolded via `npm create vite@latest -- --template react-ts`).
- **three.js + @react-three/fiber + @react-three/drei** for 3D rendering — chosen because the interstellar/galaxy view needs true 3D navigation, and it also drives the in-system view. `OrbitControls` (via drei) handles camera drag/zoom/pan in every view.
- **zustand** for shared app state: `gameTimeStore` (simulation clock) and `viewStore` (navigation level).
- Dev server: `npm run dev` (Vite, port 5173). `.claude/launch.json` is configured so the Browser preview tool can launch it by name `trc-dev`.
- Build: `npm run build` (runs `tsc -b && vite build`) — verified passing. Type-check only: `npx tsc --noEmit`.

# Project Structure:
- `src/App.tsx` — app shell: mounts the global clock (`useGameClock`), renders the HUD bars (breadcrumb nav top, time controls bottom), and switches the active scene component based on `viewStore.level`.
- `src/App.css` — all HUD styling (bars, breadcrumb, time controls, markers, info panels, draggable window, galactic placeholder).
- `src/index.css` — minimal full-viewport dark reset.
- `src/state/gameTimeStore.ts` — zustand store for the simulation clock: `simDays` (elapsed since Jan 1, `START_YEAR` = 2600), `paused`, `speedIndex` (into `SPEED_MULTIPLIERS`, Stellaris-style discrete tiers), plus `tick`/`togglePause`/`speedUp`/`slowDown` actions. Helpers `simDaysToDate` / `simDaysToYears` convert sim time for display and orbit math.
- `src/hooks/useGameClock.ts` — drives `gameTimeStore.tick()` off a `requestAnimationFrame` loop mounted once in `App.tsx`, independent of any `<Canvas>` — so the clock survives view-level Canvas remounts.
- `src/state/viewStore.ts` — zustand store for navigation: `level: 'galactic'|'interstellar'|'system'|'satellite'`, `selectedStarId`, `selectedBodyName` (the planet/star currently open in satellite view — generic name since it's not just planets), with `enterGalactic`/`enterInterstellar`/`enterSystem`/`enterSatellite`/`exitSatelliteToSystem` actions. `exitSatelliteToSystem` deliberately leaves `selectedBodyName` set (unlike `enterSystem`, which clears it) so `SolarSystemScene` can detect "we just zoomed out of a body" and start near it — see Design Decisions.
- `src/scene/orbitMath.ts` — shared helpers: `getOrbitPosition` (circular orbit position with inclination + ascending-node tilt applied), `angleForYear`, `getPlanetPosition(data, simYears)` (a planet's exact live position from data alone), and `getMoonPosition(moon, simYears)` (same idea for moons, using `MOON_TIME_DILATION` — see Design Decisions).
- `src/scene/planetData.ts` — real astronomical data (AU distances, km radii — now exposed as `radiusKm` on `PlanetData` too, for info-panel display — orbital periods, inclination + longitude of ascending node, fixed `phaseDeg`) for the Sun + 8 planets, on a single unified scale (`UNITS_PER_AU`). Also exports `SUN_RADIUS_KM`.
- `src/scene/moonData.ts` — real radius/distance/period data for each planet's major moons (not an exhaustive list — Jupiter alone has ~95 known moons; only the well-known ones are rendered, e.g. the 4 Galilean moons). `getMoonsForPlanet(name)` returns `{ totalCount, moons }` — `totalCount` is the real known total (for the info panel), `moons` is the derived, render-ready list (visual radius/orbit radius computed from real ratios, log-compressed for orbit distance and clamped for size, since real moon proportions are far too extreme to render true-to-scale within a fixed `VISUAL_RADIUS`).
- `src/scene/bodyStats.ts` — `estimateHabitability(name, orbitAU)` and `estimateSize(radiusKm)`: deliberately simple, transparent Stellaris-flavor heuristics (habitable-zone distance from Sol, radius → size class → district count) for the satellite-view info panel's "game info" section — not a real economy/habitability simulation, which this project doesn't have yet.
- `src/scene/inspectableBody.ts` — the `InspectableBody` shape (`name`, `kind: 'star'|'planet'|'moon'`, `color`, `radiusKm`, optional orbit/moon-count fields) used to feed the info window regardless of what's selected.
- `src/scene/Sun.tsx`, `src/scene/Planet.tsx`, `src/scene/Moon.tsx`, `src/scene/OrbitRing.tsx` — system-view and satellite-view marker/orbit components. `Planet.tsx`/`Moon.tsx` read global sim time directly from `gameTimeStore.getState()` in `useFrame`. All are marker-only, everywhere — no visible sphere model, including `Moon.tsx` orbiting inside satellite view now (it used to render a real small sphere there; removed for the same "marker-only until you're actually looking at its own detail view" consistency as the Sun/planets — a moon's true shape now only appears in `MoonDetailScene`).
- `src/scene/FocusableMarker.tsx` — reusable: the clickable name marker for whatever's the sole/primary subject of a satellite-view scene (the planet/star in `SatelliteViewScene`, the moon in `MoonDetailScene`). Small dot+label by default; once `focused` (the inspect window is open on it), swaps to a larger label anchored *above* the hologram (`.focused-label`) instead of sitting on top of it, where it'd compete visually with the hologram itself.
- `src/scene/MoonDetailScene.tsx` — a moon's own close-up: same structural pattern as `SatelliteViewScene` (HologramBody + FocusableMarker + Stars + exit watcher + InspectPanel) but simpler — no orbiting children, and exiting calls an `onExit` prop instead of a `viewStore` action, since it's not a distinct `ViewLevel` (see Design Decisions).
- `src/scene/CameraFocusRig.tsx` — reusable: each frame, snaps `OrbitControls.target` exactly to a live target position (no lag) and eases the camera's *distance* toward it exponentially, firing `onArrive` once within `arriveDistance` **or** after `maxFlightMs` (default 2500ms) regardless of distance — the timeout is what guarantees "Detailed View" always completes even for a fast-orbiting planet at high game speed (see Design Decisions). `OrbitControls` is disabled for the duration. Used for the "Detailed View"/"Enter System" fly-ins (system view, interstellar view) and the fly-to-a-moon inside satellite view.
- `src/scene/SelectionTracker.tsx` — reusable: every frame, *eases* `OrbitControls.target` toward a live object position (exponential smoothing, not an instant snap) while leaving user input **enabled** — the passive "camera lock" (object stays centered no matter how the player free-zooms/orbits from there). Runs at r3f priority `-2` so the target is fresh before drei's own OrbitControls update (priority `-1`) consumes it.
- `src/scene/DistanceThresholdWatcher.tsx` — reusable: fires once when camera distance crosses a min or max threshold. Distance is measured from the world origin by default, or from the current `OrbitControls.target` if a `controlsRef` is passed (needed so "zoom out to leave this view" still works correctly while camera-locked onto something off-origin, like Saturn). Drives *scroll-past-the-edge-to-navigate* between whole view levels, both directions, for every adjacent pair. Has a `graceMs` (default 500) after mount to absorb scroll-momentum carryover from the previous view.
- `src/utils/forwardWheel.ts` — `forwardWheelToCanvas`: HTML marker overlays sit in the canvas's shared event container but, being DOM siblings of the canvas rather than descendants, swallow wheel events before they reach it. Every marker's `onWheel` re-dispatches onto the actual `<canvas>` element.
- `src/scene/HologramBody.tsx` (was `HologramPlanet.tsx`, generalized) — the DEFCON/HUD-style visual used in satellite view: a core sphere, sparse lat/long wireframe grid, glowing Fibonacci-distributed dot cloud, and fresnel rim glow — all **procedural**, no texture assets. Takes `color`/`radius`/`variant` (`'planet'` = dark reflective-looking core, `'star'` = bright self-luminous core + a point light + a bigger corona-style rim) instead of a `PlanetData` object, so it works for the Sun too. Optional `onSelect` adds an invisible, slightly oversized click-catcher sphere so clicking anywhere on the hologram itself (not just its separate `FocusableMarker`) selects it.
- `src/scene/SatelliteViewScene.tsx` (was `PlanetViewScene.tsx`) — satellite-view `<Canvas>`, takes a `bodyName` (planet name or `"Sol"`). Renders `HologramBody` for the primary body (clickable via its own `onSelect` + a `FocusableMarker`), that body's moons (marker-only, via `Moon.tsx` + real orbit rings), a `DistanceThresholdWatcher` (max) that calls `exitSatelliteToSystem` on zoom-out past the edge, and an `InspectPanel` (draggable window) for whichever body — primary or a moon — is currently clicked. Selecting a moon also engages a `SelectionTracker` lock and, via the InspectPanel's optional `action` button, "Detailed View" — `CameraFocusRig` flies to it and, on arrival, swaps the whole scene over to `MoonDetailScene` (see Design Decisions).
- `src/data/starData.ts` — real nearest-neighbor stars/systems to Sol (within ~10 ly). Only Sol has `hasSystemData: true` (drillable into system view) — others are informational only for now.
- `src/scene/InterstellarScene.tsx` — interstellar-view `<Canvas>` + wrapper: star nodes (Obsidian-graph style) as marker labels only, no connecting lines yet (those represent player-plotted routes, added later). **Select-first, same model as system view** (see Design Decisions): clicking a star only locks the camera onto it (`SelectionTracker`); flying all the way in (`CameraFocusRig`) starts only via the info panel's "Enter System" button (shown when `hasSystemData`) or by manually zooming in close enough on the locked star. `enterSystem` fires on `CameraFocusRig` arrival. Has its own `onPointerMissed` deselect handler (same marker-click race guard as system view). `DistanceThresholdWatcher`s handle the unconditional zoom-in-on-Sol → system shortcut and zoom-out → galactic.
- `src/scene/GalacticViewScene.tsx` — galactic-view placeholder: starfield + "GALACTIC VIEW — Not yet charted" text, intentionally not built out further yet.
- `src/components/Breadcrumb.tsx` — top HUD nav, generic level labels only: GALAXY › INTERSTELLAR › SYSTEM › SATELLITE, clickable to jump up a level.
- `src/components/LocationLabel.tsx` — small subtitle under the app title showing the *specific* location, e.g. "Sol System — Mars".
- `src/components/TimeControls.tsx` — bottom-center HUD: current in-game date, pause/play, speed up/down, 5-pip speed indicator.
- `src/components/DraggableWindow.tsx` — generic movable HUD window (pointer-based title-bar drag, no resize) — currently used only by `InspectPanel`, but written generic in case other floating panels are wanted later.
- `src/components/InspectPanel.tsx` — the satellite-view "inspect a body" window: wraps `DraggableWindow`, renders an `InspectableBody`'s basic info (type/radius/orbit/moon count) plus, for planets/moons, the `bodyStats.ts`-derived game info (size class, districts, habitability). Stars skip the game-info section (doesn't apply to them yet). Optional `action` prop (`{label, pendingLabel, pending, onClick}`) renders a "Detailed View"-style button (or, while `pending`, a status line) — used by `SatelliteViewScene` for a selected moon's fly-in.

# Design Decisions Made So Far:
- **True-to-scale solar system**: orbital distances and body radii both use the *same* real-world scale factor (1 AU = `UNITS_PER_AU` scene units, currently 20), so relative proportions are physically accurate.
  - Tradeoff: at true scale, planet spheres are geometrically sub-pixel at any usable zoom. Fixed DEFCON-style: each body has a small constant-screen-size marker (circle + label, via drei `Html`) at its exact true 3D position.
- **Orbital tilts are real, not decorative**: real J2000 inclination + longitude of ascending node values, via `orbitMath.getOrbitPosition`.
- **Global time engine (Stellaris-style)**: single `gameTimeStore` holds `simDays` since 2600-01-01, advanced by a `requestAnimationFrame` loop independent of any Canvas. 5 discrete speed tiers + pause. All orbital motion is a **pure function of `simDays`**, never per-frame delta accumulation.
- **View levels as separate `<Canvas>` per level**: each mounts its own Canvas rather than sharing one camera rig.
  - **Gotcha**: each remount creates a new WebGL context; heavy back-and-forth navigation in one tab can hit the browser's context limit (`THREE.WebGLRenderer: Context Lost`, frozen scene) — fix is a hard tab reload, not a code bug.
- **In system view: select = lock on immediately, not click-to-jump.** Clicking a planet or the Sun both selects it (info panel + "Detailed View" button — now available for the Sun too, see below) *and* immediately engages the camera lock (`SelectionTracker`), without requiring zoom-in first. Zooming out far enough still exits to interstellar exactly as if nothing were locked (`controlsRef`-aware `DistanceThresholdWatcher`). Clicking "Detailed View" triggers `CameraFocusRig`'s fly-in and transitions into satellite view on arrival. Clicking empty space clears the selection/lock.
- **Manually zooming in on a locked-on body also enters satellite view** (not just the "Detailed View" button) — a `DistanceThresholdWatcher` (mode `min`, measured from the tracked body via `controlsRef`, threshold `3`) fires `enterSatellite` once the player zooms in close enough on their own. Works for the Sun too, not just planets.
- **Scroll-past-the-edge navigation between whole levels**, wired both directions for every adjacent pair, each with a CSS fade/scale-in (`.view-transition` in `App.tsx`) regardless of what triggered the swap.
- **Interstellar view uses real star data**: nearest real stars/systems to Sol within ~10 ly, real RA/Dec/distance → Cartesian. Only Sol is drillable into a system view. Hub-and-spoke lines were removed — those represent player-plotted routes, not something drawn automatically.
- **Galactic view is intentionally a stub** per explicit instruction.
- **Celestial body visuals are procedural, not textured**: the DEFCON/HUD "hologram" look (`HologramBody.tsx`) is Three.js geometry + a small custom shader, no texture assets — deliberately chosen to match the vector-art DEFCON aesthetic. An `assets/` folder exists at the project root for future binary assets if ever wanted (user's convention: subfolder per asset type).
- **Marker/orbit line colors are bright cyan** (`#2fd8ff`) — an earlier dim navy was too hard to see.
- **Markers have `user-select: none`**: without it, real-mouse cursor jitter between mousedown/mouseup gets hijacked into a native text-selection drag instead of registering as a click.
- **Exit thresholds across all levels are tuned so the current view shrinks to "basically a dot" before handing off** — not a modest zoom-out. System→interstellar: `26000` (default start ~10500, see below). Interstellar→galactic: `3500`. Satellite→system: `130`/`160` (exit/max), against a visual radius of `3`.
- **`onPointerMissed` race with marker clicks**: r3f's `<Canvas onPointerMissed>` fires for any click inside the canvas's shared event container that doesn't raycast-hit a 3D object — including clicks on HTML marker overlays (portaled into that same container so drei's `Html` can render above the canvas). Clicking a marker fires the marker's own `onClick` *and* `onPointerMissed` almost simultaneously; without a guard, the miss handler undoes the selection in the same tick. Fixed everywhere `onPointerMissed` is used (system, interstellar, satellite) by checking `event.target.closest('.planet-marker')` and ignoring the miss when the click landed on a marker. **Any future `onPointerMissed` usage needs the same guard.**
- **`CameraFocusRig` snaps its target exactly each frame (never lerps it), and has a `maxFlightMs` timeout**: an earlier version lerped the target, which left it perpetually lagging a fast-moving planet (steady-state lag ≈ orbital speed / rig speed) — since arrival is judged against the *true* live position, that lag could stay ≥ `arriveDistance` forever, breaking "Detailed View" for fast planets (Mercury, especially at high game speed) while time was running. Snapping the target fixed most of it, but a *second*, subtler issue remained: even with an exact snap, each frame's offset partially reflects how far the target itself moved since last frame (not just how far the camera closed in), so a fast-enough orbit can still prevent the instantaneous distance from ever dipping under `arriveDistance`. Rather than chase a perfect closed-form fix for every possible orbital-speed/game-speed combination, added a hard timeout (`maxFlightMs`, default 2500ms) that force-arrives regardless of distance — this is what actually, robustly fixes "only works when the planet happens to be moving toward the camera." Verified at max game speed on Mercury (the fastest, worst-case planet).
- **Marker dot is centered independently of the label**: `.planet-marker` centers the dot specifically (its own `translate(-50%,-50%)`), with the label absolutely positioned beside it — not a single transform on the whole flex row (which centered the row's bounding box, visibly offsetting the dot from the true point/off the orbit ring).
- **`DistanceThresholdWatcher` has a `graceMs` (default 500) after mount** to absorb scroll-momentum carryover into a freshly-mounted Canvas, preventing an unintended cascade through multiple level transitions from one continuous zoom gesture.
- **`SelectionTracker` eases continuously (never snaps)**, unlike `CameraFocusRig`'s exact-snap-plus-eased-distance: it has no "arrival" check to break, so continuous eased lag is purely cosmetic (and desirable — smooth pan on lock-on) here, whereas the same kind of lag was a functional bug in `CameraFocusRig`.
- **System view starts far away on a fresh arrival, but "somewhat close" when returning from satellite view via zoom-out.** A fresh arrival (breadcrumb, interstellar fly-in) starts at `FAR_START` (`[0, 6300, 8400]`, distance ~10500) so the whole system reads as a small distant cluster, symmetric with the "shrink to a dot" exit feel. But if `viewStore.selectedBodyName` is still set at mount (meaning we just zoomed out of that body's satellite view — `exitSatelliteToSystem` deliberately doesn't clear it), `SolarSystemScene` instead starts the camera at `NEAR_START_DISTANCE` (`18` units) from that body's live position *and* pre-selects/locks onto it immediately — so leaving a planet's close-up reads as smoothly stepping down a level of detail while staying near it, not jumping to an unrelated distant view. Both the initial camera position and the initial `selectedName` are computed once via a ref captured at mount (`continuityBodyRef`), deliberately not reactive to later state changes.
- **Moon orbits are tied to the game clock but time-dilated by 60x (`MOON_TIME_DILATION`)**: real moon orbital periods (hours to weeks) are far too fast to animate at the same accelerated day-scale everything else uses — a real-speed Phobos orbit would complete in a fraction of a real second and look like a flicker. Rather than decouple moons from the game clock entirely (which would mean they keep moving while the game is paused, inconsistent with everything else), their effective period is multiplied by 60 before being run through the same `simDays`-driven math as planets — so pausing/speeding up the game still affects moons consistently, but they're visually legible. Relative speed differences between moons (closer/faster vs. farther/slower) are preserved from the real ratios.
- **Moon sizes/orbit distances are hand-scaled from real ratios, not literally true-to-scale**: real moon-to-planet size and distance ratios vary too wildly to render directly (Jupiter dwarfs its moons far more than Earth dwarfs the Moon) within a fixed `VISUAL_RADIUS` primary body. `moonData.ts` computes visual radius from the real `moon/planet` radius ratio (clamped to a visible min/max) and orbit radius from the real distance ratio (log-compressed) — the real *ordering* (bigger/farther reads as bigger/farther) is preserved even though absolute proportions aren't literal.
- **Only major/well-known moons are rendered per planet**, not the real full count (Jupiter has ~95 known moons) — rendering all of them would be unreadable clutter. The info panel's "Moons" field shows the real total count regardless of how many are actually rendered, so the number is honest even though the visual is curated.
- **The Sun is now inspectable via satellite view too**, not just planets — this is *why* `HologramBody` was generalized from `HologramPlanet` (added a `variant: 'star'` for a bright self-luminous look vs. planets' dark reflective one) and why `viewStore`'s `selectedPlanetName` was renamed to `selectedBodyName` / `enterPlanet` to `enterSatellite` throughout. Sets up for other future "satellite view" subjects (asteroids, black holes) per the user's explicit framing.
- **"Game info" (habitability/districts) is a transparent placeholder heuristic** (`bodyStats.ts`), not a real simulation — this project doesn't have gameplay/economy systems yet. Worth replacing with real mechanics once those exist rather than building further on the heuristic.
- **The inspect window is a real drag-anywhere HUD window** (`DraggableWindow.tsx`), not a fixed corner panel — pointer-capture-based drag on the title bar, no resize. Re-centers on whichever body is newly selected; stays wherever dragged until a different body is selected.
- **Interstellar view now uses the same select-first model as system view** (this was the last open roadmap item on navigation consistency): clicking a star locks the camera onto it via `SelectionTracker` (smooth eased pan, `OrbitControls` still enabled) instead of immediately flying in with `CameraFocusRig`. The actual fly-in only starts from an explicit "Enter System" button (shown in the info panel when the star `hasSystemData`) or by manually zooming in close on the locked star (`DistanceThresholdWatcher` min, measured via `controlsRef` like system view's `ENTER_SATELLITE_DISTANCE`) — mirrors system view's select-vs-"Detailed View" split exactly. The unconditional "scroll straight through toward Sol" shortcut (measured from world origin, not the lock target) is preserved unchanged for players who zoom straight in without clicking anything first.
- **Moons get their own "Detailed View," structured as a mode-switch inside `SatelliteViewScene`, not a new `ViewLevel`.** Selecting a moon (click) opens its `InspectPanel` and engages `SelectionTracker` on it; the panel's "Detailed View" action flies `CameraFocusRig` to the moon's live position, and `onArrive` swaps the scene's content to `MoonDetailScene` (moon rendered as its own `HologramBody`, real habitability via the parent planet's `orbitAU`). Zooming out of `MoonDetailScene` calls a plain `onExit` callback that flips back to the primary body's view — no `viewStore.level` change at all, so the breadcrumb/exit-to-system behavior at the outer satellite level is completely unaffected. The mode-switch is wrapped in its own `.view-transition`-keyed div (`'primary'` vs `` `moon:${name}` ``) purely so the swap gets the same fade the rest of the app uses for level changes — this is a **second, independent instance** of the "key change forces remount + CSS fade replay" trick already used by `App.tsx`'s `ActiveScene`, just scoped one level deeper. **Gotcha found while wiring this up**: `CameraFocusRig`'s `onArrive` must also clear the local "flying to X" state (not just set "focused on X"), otherwise it stays truthy after zooming back out and the flight (and thus the mode-switch into detail view) re-triggers itself immediately — this doesn't happen at the top `viewStore` level because a level change there fully unmounts the component, discarding state for free; a same-component mode-switch has no such reset and needs it done explicitly.
- **Moon habitability reuses `bodyStats.estimateHabitability` as-is, fed the *parent planet's* `orbitAU`** rather than adding separate per-moon habitability data — a moon shares its planet's distance from Sol, so the same habitable-zone heuristic applies without inventing a second one. `InspectPanel` computes habitability for `kind !== 'star'` now (previously `kind === 'planet'` only). **Gotcha**: the existing "Orbit" AU/period-years row is keyed off the same `orbitAU` field, so naively enabling habitability for moons made that row appear too, displaying the *parent's* solar orbit under a moon's own name with a blank year figure (no `orbitPeriodYears` set for moons) — looked exactly like a bug. Fixed by gating that specific row to `body.kind === 'planet'`, while the moon's own real orbit still shows correctly via the separate `orbitPeriodDays` row.
- **`HologramBody`'s click-catcher is a separate invisible mesh (radius ×1.15, `opacity: 0`, `depthWrite: false`), not an `onClick` on the visible meshes.** Opacity doesn't affect raycasting in three.js (only `object.visible` does), so a fully transparent mesh still catches clicks reliably — simpler and more robust than adding handlers to multiple existing meshes (core/wireframe/rim) with different geometries and blend modes.
- **A focused/inspected satellite-view subject gets a bigger label anchored above the hologram (`FocusableMarker`'s `focused` branch, `.focused-label` CSS) instead of the small dot+label sitting on it** — avoids the label competing visually with the hologram itself once a body is the clear subject of attention. Non-focused subjects (i.e. anything not currently open in the inspect window) still use the small marker.
- **Known testing-environment caveat (not a code issue)**: the sandboxed Browser-pane tab used for verifying this session's changes intermittently lost its WebGL context (`THREE.WebGLRenderer: Context Lost`) and, separately, stalled its `requestAnimationFrame` loop (game clock and `CameraFocusRig` both frozen mid-flight) after routine view-level navigation — reproduced even on totally unmodified, pre-existing navigation paths (fresh tab, first-ever remount), so it's an artifact of that automation environment, not a regression from these changes. Structural/DOM verification (correct markers rendered, correct panel fields, correct button gating, state transitions via `get_page_text`) was used as a fallback where full animated-flight verification wasn't possible; a real browser session should behave normally since Context.md already documented the WebGL-context-limit gotcha as pre-existing.
