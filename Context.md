TR: Conquest
# Overview:
"Terra Relicta: Conquest" is a web-based grand strategy game.

# Setting / Lore:
## FTL Travel
Two methods of faster-than-light travel exist:
- **Warp Drive** — uses "Exotic Matter," a form of matter found on certain planets with a higher mass-energy conversion rate than normal matter. Warp drives use exotic matter to warp and move space itself to travel.
- **Hyperdrive** — uses "Hyperium," extremely rare to find naturally but yields effectively infinite energy. Hyperium cannot be broken up/subdivided, so each ship equipped with a hyperdrive is extremely valuable. Hyperdrives use hyperium to access "hyperspace," a dimension outside the normal universe where time passes faster, allowing FTL travel. (Exact mechanics of hyperspace aren't important to nail down yet.)
- Both exotic matter and hyperium don't just power FTL drives — they also power the entire ship's systems and weapons.

## STL (sub-light) Travel
- STL warp drives tend to use **antimatter**, harvested via massive particle accelerators or extracted from locations with high "antimatter density."

## Timeline
- The game's campaign starts in the **year 2600**.

# Visual Style / UX Reference:
- The game should look like a tactical map, similar to **DEFCON** (see reference screenshots: minimalist neon vector map, arcs for missile/unit trajectories, glowing markers, DEFCON-style HUD/side panels).
- Scale/view structure (4 zoom levels, see View Levels below):
  - **Satellite view** (internal `level: 'satellite'`, was called "planet view" — renamed since it now also handles stars and, eventually, other close-up-inspectable things like asteroids/black holes): close-up of a single planet or star, with any of its moons.
  - **System view**: 2D-ish top-down (like DEFCON's flat world map).
  - **Interstellar view**: 3D, styled like an **Obsidian graph view** — nodes (nearby stars) connected by edges.
  - **Galactic view**: 3D, same graph style, zoomed out to galaxy scale (placeholder only so far).

# Tech Stack:
- **Vite + React + TypeScript** (scaffolded via `npm create vite@latest -- --template react-ts`).
- **three.js + @react-three/fiber + @react-three/drei** for 3D rendering — chosen because the interstellar/galaxy view needs true 3D navigation, and it also drives the in-system view. `OrbitControls` (via drei) handles camera drag/zoom/pan in every view.
- **zustand** for shared app state: `gameTimeStore` (simulation clock) and `viewStore` (navigation level).
- Dev server: `npm run dev` (Vite, port 5173). `.claude/launch.json` is configured so the Browser preview tool can launch it by name `trc-dev`.
- Build: `npm run build` (runs `tsc -b && vite build`) — verified passing. Type-check only: `npx tsc --noEmit`.

# Project Structure:
- `src/App.tsx` — app shell: mounts the global clock (`useGameClock`), renders the HUD bars (breadcrumb nav top, time controls bottom), and switches the active scene component based on `viewStore.level`.
- `src/App.css` — all HUD styling (bars, breadcrumb, time controls, markers, info panels, draggable window, galactic placeholder).
- `src/index.css` — minimal full-viewport dark reset.
- `src/state/gameTimeStore.ts` — zustand store for the simulation clock: `simDays` (elapsed since Jan 1, `START_YEAR` = 2600), `paused`, `speedIndex`, and `mode: 'normal'|'tactical'` — two *rates* on one clock, not two clocks (see Design Decisions), at `NORMAL_DAYS_PER_SECOND` (6) vs `TACTICAL_DAYS_PER_SECOND` (one sim-second per real second). Speed tiers differ per mode (`speedMultipliersFor`), and `setMode` clamps `speedIndex` into the new mode's range without touching `paused`. Helpers `simDaysToDate`/`simDaysToYears` convert for display and orbit math; `simSecondsToDays`/`simDaysToSeconds` are the single conversion point for combat, which is authored in seconds but stored as absolute `simDays` deadlines like everything else; `formatClockTime` renders the wall clock shown in tactical mode.
- `src/hooks/useGameClock.ts` — drives `gameTimeStore.tick()` off a `requestAnimationFrame` loop mounted once in `App.tsx`, independent of any `<Canvas>` — so the clock survives view-level Canvas remounts.
- `src/data/combatData.ts` — the combat vocabulary: `DamageType` (energy/kinetic/missile/torpedo) and the `DAMAGE_PROFILES` multiplier matrix against each defense layer; `ComponentKind` (weapons/utility/core) and `OVERALL_WEIGHTS` for the blended bar; `WeaponMount`/`DefenseProfile`/`CombatProfile` shapes; the `WEAPON_TYPES` archetype catalog; per-hull profiles (`CIVILIAN_`/`CORVETTE_`/`FRIGATE_`/`DESTROYER_`/`CRUISER_`/`BATTLESHIP_PROFILE`); FTL charge durations; and the `weaponsEffectiveness`/`utilityEffectiveness` degradation curves. Kept separate from `shipData.ts` (hulls and drives) so "what can this ship shoot with" has one home. Every number is a picked balance value, not derived from anything physical — grouped as named exports so a future tech tree has one place to scale from.
- `src/scene/combatArena.ts` — the arena's coordinate system and its pathfinding lattice, kept deliberately separate (see Phase 4 in Design Decisions for why the two used to be conflated, and the bug that caused). `ArenaPoint` (`{x,y,z}` in real, continuous arena units) is the type actual game state is stored in — ship/obstacle/window-centre positions — and is density-independent by construction. `GridNode` (a lattice index) exists only as an ephemeral planning aid, converted to/from `ArenaPoint` via `nodeToArenaPosition`/`arenaPositionToNode` at the moment a route needs computing. Also holds `GridDensity` (subdivision count only — physical `ARENA_SPAN_UNITS` is constant, so weapon ranges mean the same thing at every setting), `isInsideWindow` (density-free — the window's *physical* size never changes), the `CombatObstacle` shape (`position: ArenaPoint`) plus `isPointBlocked`/`segmentIntersectsSphere`/`hasLineOfFire`/`segmentClearsObstacles`, 26-way `neighborsOf`, and `latticePath` — greedy in open space, A* bounded by `boundsFor(from, to, margin)` when a body actually clips the straight route. Pure/stateless throughout.
- `src/scene/combatResolution.ts` — the combat simulation, pure functions over `(engagements, ships, simDays, rng)` with no store access, mirroring `shipPhysics.planMove`'s "physics computes, caller applies" split. Holds `applyShot` (the three-layer damage walk with raw-carryover overflow), `pickComponent`, `overallHealthFraction`, `stepEngagements` (one fixed timestep: approach → movement → shield regen → firing → escapes), `syncEngagements` (roster reconciliation against where ships actually are), `approachNode`/`orderParticipantTo`, and `planFtlCharge`/`ftlChargeSeconds`. The RNG is injected so tests can seed it — this is the primary verification path for combat.
- `src/state/combatStore.ts` — live engagements: `Engagement` (location key, density, participants, `resolvedThroughSimDays`) and `CombatParticipant` (lattice node, in-flight hop, queued path, per-mount weapon timers, chosen target + target component). Also `areHostile`/`sideFor`/`combatLocationKey`, and `autoTacticalOnEngage` (whether a fight yanks the clock into tactical). Deliberately holds only what's transient to a fight — persistent damage lives on `ShipInstance.combat`.
- `src/hooks/useCombatResolver.ts` — drives combat off the clock the same way `useShipOrderSettler` does (subscribing to `simDays`, not its own rAF loop), so battles resolve regardless of which view's `<Canvas>` is mounted, or whether anyone is watching. Reconciles the roster, steps in strict whole timesteps (carrying sub-step remainder — see Design Decisions), applies damage/destructions, turns completed FTL charges into real move orders, and keeps the clock's mode in sync with whether any fight is live.
- `src/components/FleetManagement.tsx` — the Fleet Management window's three subtabs. **Fleet Manager**: every ship in service with live integrity and current action. **Ship Designer**: a read-only catalog of preset hulls — components, defenses, a per-mount armament table, raw DPS (labelled raw precisely because it ignores the defense matrix), and the damage-type matchups the loadout brings. **Strategizer**: reserved, deliberately empty.
- `src/scene/CombatViewScene.tsx` — the combat "detailed view": an engagement rendered as a navigable 3D arena. Structurally a sibling of `SatelliteViewScene` (own Canvas, OrbitControls, exit-by-zooming-out watcher, panels outside the Canvas) but its subject is a fight. Owns click-to-move (latching `holdPosition`) and right-click-to-target, and exits itself when the engagement ends.
- `src/scene/CombatGrid.tsx` — the lattice visual: interior grid, node points, and outer cage as three single-draw-call `BufferGeometry` layers, with interior opacity scaling *down* as density rises. Also exports `nearestNodeToRay`, which scores every node by perpendicular distance to the click ray (a ray passes through many nodes, so a hit test can't answer "what did they click").
- `src/scene/CombatShipMarker.tsx` — a combatant in the arena. Reads its position from the store every frame via `useFrame` + `getState()` rather than props, since the resolver rewrites participant state constantly. Carries an integrity bar and a pulsing FTL-charge badge directly on the marker.
- `src/scene/CombatPathLine.tsx` — a ship's committed lattice route. Drawn for every participant, not just the selected ship: it's both the feedback for your own order and the read on where the enemy is going, and it's what makes the grid constraint visible (routes staircase rather than glide).
- `src/components/CombatPanel.tsx` — the per-engagement command surface: full roster with live integrity per side, grid-density control, and (for a selected player ship) firing target, focus-fire component, and manual/auto movement state. Deliberately distinct from `ShipPanel` (a per-ship inspector available everywhere), and the one `DraggableWindow` with no close button.
- `src/state/viewStore.ts` — zustand store for navigation: `level: 'galactic'|'interstellar'|'system'|'satellite'`, `selectedStarId`, `selectedBodyName` (the planet/star currently open in satellite view — generic name since it's not just planets), `inViewSelection` (whatever's selected *within* the active scene, in that scene's own id space — star id for interstellar, body/moon name for system/satellite; see Design Decisions), `lockOnEnabled` (whether selecting something eases the camera onto it — see Design Decisions), with `enterGalactic`/`enterInterstellar`/`enterSystem`/`enterSatellite`/`exitSatelliteToSystem`/`selectInView`/`toggleLockOn` actions. `exitSatelliteToSystem` deliberately leaves `selectedBodyName` set (unlike `enterSystem`, which clears it) so `SolarSystemScene` can detect "we just zoomed out of a body" and start near it — see Design Decisions. `pendingSelectBodyName` (a separate field) was retired this session, folded into `inViewSelection`.
- `src/scene/orbitMath.ts` — shared helpers: `getOrbitPosition` (circular orbit position with inclination + ascending-node tilt applied), `angleForYear`, `getPlanetPosition(data, simYears)` (a planet's exact live position from data alone), and `getMoonPosition(moon, simYears)` (same idea for moons, using `MOON_TIME_DILATION` — see Design Decisions).
- `src/scene/planetData.ts` — real astronomical data (AU distances, km radii — now exposed as `radiusKm` on `PlanetData` too, for info-panel display — orbital periods, inclination + longitude of ascending node, fixed `phaseDeg`) for the Sun + 8 planets, on a single unified scale (`UNITS_PER_AU`). Also exports `SUN_RADIUS_KM` and `AU_IN_KM` (the latter now reused by `shipPhysics.ts` for real-scale travel-time math, not just the rendering scale).
- `src/scene/moonData.ts` — real radius/distance/period data for each planet's major moons (not an exhaustive list — Jupiter alone has ~95 known moons; only the well-known ones are rendered, e.g. the 4 Galilean moons). `getMoonsForPlanet(name)` returns `{ totalCount, moons }` — `totalCount` is the real known total (for the info panel), `moons` is the derived, render-ready list (visual radius/orbit radius computed from real ratios, log-compressed and now also hard-clamped (`MAX_ORBIT_RADIUS = 12`) for orbit distance, clamped for size, since real moon proportions are far too extreme to render true-to-scale within a fixed `VISUAL_RADIUS`).
- `src/scene/bodyStats.ts` — `estimateHabitability(name, orbitAU)` and `estimateSize(radiusKm)`: deliberately simple, transparent Stellaris-flavor heuristics (habitable-zone distance from Sol, radius → size class → district count) for the satellite-view info panel's "game info" section — not a real economy/habitability simulation, which this project doesn't have yet.
- `src/scene/inspectableBody.ts` — the `InspectableBody` shape (`name`, `kind: 'star'|'planet'|'moon'`, `color`, `radiusKm`, optional orbit/moon-count fields) used to feed the info window regardless of what's selected.
- `src/scene/Sun.tsx`, `src/scene/Planet.tsx`, `src/scene/Moon.tsx`, `src/scene/OrbitRing.tsx` — system-view and satellite-view marker/orbit components. `Planet.tsx`/`Moon.tsx` read global sim time directly from `gameTimeStore.getState()` in `useFrame`. `Sun.tsx`/`Planet.tsx` (system view) stay marker-only, no visible sphere. `Moon.tsx` (satellite view) now renders an actual `HologramBody` sized to `moon.visualRadius` alongside its marker dot — reversed from an earlier decision to keep it marker-only; see Design Decisions ("Moon hologram restored").
- `src/scene/FocusableMarker.tsx` — reusable: the clickable name marker for whatever's the sole/primary subject of a satellite-view scene (the planet/star in `SatelliteViewScene`, the moon in `MoonDetailScene`). Always renders as a prominent label anchored *above* the hologram (`.focused-label`) rather than sitting on top of it — it's always shown for as long as that body is the view's subject, not gated on the inspect window being open (see Design Decisions).
- `src/scene/MoonDetailScene.tsx` — a moon's own close-up: same structural pattern as `SatelliteViewScene` (HologramBody + FocusableMarker + Stars + exit watcher + InspectPanel) but simpler — no orbiting children, and exiting calls an `onExit` prop instead of a `viewStore` action, since it's not a distinct `ViewLevel` (see Design Decisions).
- `src/scene/CameraFocusRig.tsx` — reusable: each frame, snaps `OrbitControls.target` exactly to a live target position (no lag) and eases the camera's *distance* toward it exponentially, firing `onArrive` once within `arriveDistance` **or** after `maxFlightMs` (default 2500ms) regardless of distance — the timeout is what guarantees "Detailed View" always completes even for a fast-orbiting planet at high game speed (see Design Decisions). `OrbitControls` is disabled for the duration. Used for the "Detailed View"/"Enter System" fly-ins (system view, interstellar view) and the fly-to-a-moon inside satellite view.
- `src/scene/SelectionTracker.tsx` — reusable: every frame, *eases* `OrbitControls.target` toward a live object position (exponential smoothing, not an instant snap) while leaving user input **enabled** — the passive "camera lock" (object stays centered no matter how the player free-zooms/orbits from there). Runs at r3f priority `-2` so the target is fresh before drei's own OrbitControls update (priority `-1`) consumes it.
- `src/scene/DistanceThresholdWatcher.tsx` — reusable: fires once when camera distance crosses a min or max threshold. Distance is measured from the world origin by default, or from the current `OrbitControls.target` if a `controlsRef` is passed (needed so "zoom out to leave this view" still works correctly while camera-locked onto something off-origin, like Saturn). Drives *scroll-past-the-edge-to-navigate* between whole view levels, both directions, for every adjacent pair. Has a `graceMs` (default 500) after mount to absorb scroll-momentum carryover from the previous view.
- `src/utils/forwardWheel.ts` — `forwardWheelToCanvas`: HTML marker overlays sit in the canvas's shared event container but, being DOM siblings of the canvas rather than descendants, swallow wheel events before they reach it. Every marker's `onWheel` re-dispatches onto the actual `<canvas>` element.
- `src/scene/HologramBody.tsx` (was `HologramPlanet.tsx`, generalized) — the DEFCON/HUD-style visual used in satellite view: a core sphere, sparse lat/long wireframe grid, glowing Fibonacci-distributed dot cloud, and fresnel rim glow — all **procedural**, no texture assets. Takes `color`/`radius`/`variant` (`'planet'` = dark reflective-looking core, `'star'` = bright self-luminous core + a point light + a bigger corona-style rim) instead of a `PlanetData` object, so it works for the Sun too. Optional `onSelect` adds an invisible, slightly oversized click-catcher sphere so clicking anywhere on the hologram itself (not just its separate `FocusableMarker`) selects it.
- `src/scene/SatelliteViewScene.tsx` (was `PlanetViewScene.tsx`) — satellite-view `<Canvas>`, takes a `bodyName` (planet name or `"Sol"`). Renders `HologramBody` for the primary body (clickable via its own `onSelect` + a `FocusableMarker`), that body's moons (now each its own `HologramBody` too, not marker-only — via `Moon.tsx` + real orbit rings), any ships resting in orbit here (`SatelliteShipMarker`), a `DistanceThresholdWatcher` (max) that calls `exitSatelliteToSystem` on zoom-out past the edge, and an `InspectPanel`/`ShipPanel` (draggable window, ship panel taking priority) for whichever body/moon/ship is currently selected. Selecting a moon also engages a `SelectionTracker` lock and, via the InspectPanel's optional `action` button, "Detailed View" — `CameraFocusRig` flies to it and, on arrival, swaps the whole scene over to `MoonDetailScene` (see Design Decisions). Selection is `viewStore.inViewSelection`-driven (not local state) so the `Outliner` can select entries here too; a `useEffect` pops back out of `MoonDetailScene` if that selection points elsewhere.
- `src/data/starData.ts` — real nearest-neighbor stars/systems to Sol (within ~10 ly). Only Sol has `hasSystemData: true` (drillable into system view) — others are informational only for now. Exports `starScenePosition` (was a local `toScenePos` inside `InterstellarScene.tsx`, promoted here so `shipPhysics.ts` can compute the same on-screen star position for travel math without a scene-importing-scene dependency).
- `src/data/shipData.ts` — ship drive types (`WarpDrive`, `HyperDrive`; every ship also implicitly has a `reactionDrive: true` for sublight, since warp/hyperdrives don't handle real-space movement) and `ShipClass` (name/`reactionDrive`/`ftlDrives[]` — an array, not a single optional drive, so a future ship combining warp *and* hyperdrive doesn't need a shape change; no longer carries a `color` — see `FleetAllegiance` below). `WARP_SPEED_TIERS_C` (`[0.5, 1, 10, 100, 314]`) and `HYPERDRIVE_BASE_COOLDOWN_DAYS` (27) are real data, not wired to a tech tree yet (none exists). `SHIP_CLASSES` currently holds two example classes: Swift Courier (10c warp) and Star Jumper (27-day hyperdrive). Also exports `FleetAllegiance` (`'player'|'friendly'|'neutral'|'hostile'`) and `ALLEGIANCE_COLORS`/`ALLEGIANCE_LABELS` — see Design Decisions.
- `src/state/shipStore.ts` — zustand store: `ships: ShipInstance[]` (`id`/`classId`/`name`/`allegiance`/`location`/`order`/`hyperdriveReadySimDays`) + `selectedShipId` (global — not per-scene local state, so selection survives view changes, per the explicit requirement) + `spawnShip`/`removeShip`/`selectShip`/`setShipOrder`/`setShipLocation`. Deliberately dependency-free of the scene/physics layer (matches `viewStore`/`gameTimeStore`'s existing convention) — callers resolve the actual travel math via `shipPhysics.planMove` and hand the store an already-computed result. `ShipLocation` (where a ship rests: `orbiting` a body with a small cosmetic `offset`, a static `system-point`, `star`, or `interstellar-point`) and `MoveOrder` (`destination`/`departSimDays`/`arrivalSimDays`/`space`/`startPosition`/`endPosition`) are the two halves of "where a ship is" — see Design Decisions for why travel is a pure function of simDays rather than accumulated per-frame movement.
- `src/scene/shipPhysics.ts` — all the real-scale travel math in one place: real constants (`SPEED_OF_LIGHT_KM_S`, `LY_IN_KM` derived from it, `REACTION_DRIVE_SPEED_KM_S`), `KM_PER_SYSTEM_UNIT`/`KM_PER_INTERSTELLAR_UNIT` (the same `AU_IN_KM`/`UNITS_PER_AU` and `LY_IN_KM`/`UNITS_PER_LY` ratios the rendering scale already uses, so ship speed is consistent with what's on screen), `getShipRenderPosition` (pure function of simDays — lerps between an order's start/end once travelling, or resolves a resting `ShipLocation` otherwise), `getShipStatusText` (the "In Sol System, orbiting Earth" / "En route to X" / "In Deep Space" display text), and `planMove` (the single entry point that turns "ship X, go to Y" into a `MoveOrder`, an instant hyperdrive jump, a cooldown rejection, or nothing — including picking which drive to use). Also `shipSystemId` (which system, if any, a ship currently belongs to — shared by `SolarSystemScene`'s membership filter and `InterstellarScene`'s presence-badge map) and `satelliteOrbitLocalPosition` (the stable per-ship-id hash placement `SatelliteShipMarker` uses).
- `src/scene/ShipMarker.tsx` — a spawned ship's marker: a small triangle (not the circular planet/star dot) so ships read as visually distinct from celestial bodies, colored by `ALLEGIANCE_COLORS[ship.allegiance]` (not the ship's class — see Design Decisions). Position comes from `getShipRenderPosition` each frame (same pattern as `Planet.tsx`); also the place that notices an order's `arrivalSimDays` has passed and calls `setShipLocation` to settle it — harmless if this fires late (nothing else is watching) since the render position already clamps at the destination regardless of when the bookkeeping catches up. Supports `selected`/`hovered` like other markers.
- `src/scene/SatelliteShipMarker.tsx` — the satellite-view equivalent of `ShipMarker`, for ships resting in orbit around the body the current satellite view is showing. Same triangle visual, but positioned via `shipPhysics.satelliteOrbitLocalPosition` (a stable per-ship-id hash placement near the hologram) instead of a physically resolved position, since a ship's real `orbiting` offset is in system-AU units that have no meaningful translation into this view's unrelated hologram-visual-radius scale — see Design Decisions.
- `src/scene/ShipPanel.tsx` — the selected ship's info window (`DraggableWindow`-based): class, drives, and a live location/status line (subscribes to `simDays` directly, same pattern `TimeControls` already uses, so it updates continuously while a ship travels, not just at the moment the panel opened).
- `src/scene/DeepSpaceClickPlane.tsx` — an invisible full-coverage ground-plane mesh added to both `SolarSystemScene` and `InterstellarScene`, the canonical "empty space" target for left-click (deselect) and right-click (issue a move order to a deep-space point). Needed because right-clicking true empty space has nothing to raycast against otherwise. Its own click handlers carry the same `.planet-marker`/`.ship-marker` closest-check guard as every other `onPointerMissed` use in this codebase (see Design Decisions — adding a full-coverage raycast target changed what "a miss" means at the plane's own event level, not just at the Canvas level).
- `src/components/DebugConsole.tsx` — dev-only ship-spawning tool (pick a class + a body to spawn "orbiting," at a small fixed cosmetic offset from a small ring of presets, an allegiance, spawn/remove). Toggled with the backtick key. Only ever rendered behind `import.meta.env.DEV` in `App.tsx` — see Design Decisions for why that's the real access-control boundary, not the keybind.
- `src/scene/InterstellarScene.tsx` — interstellar-view `<Canvas>` + wrapper: star nodes (Obsidian-graph style) as marker labels only, no connecting lines yet (those represent player-plotted routes, added later). **Select-first, same model as system view** (see Design Decisions): clicking a star only locks the camera onto it (`SelectionTracker`); flying all the way in (`CameraFocusRig`) starts only via the info panel's "Enter System" button (shown when `hasSystemData`) or by manually zooming in close enough on the locked star. `enterSystem` fires on `CameraFocusRig` arrival. Has its own `onPointerMissed` deselect handler (same marker-click race guard as system view). `DistanceThresholdWatcher`s handle the unconditional zoom-in-on-Sol → system shortcut and zoom-out → galactic. `StarNode` also renders a no-text `fleetAllegiances` presence badge (see Design Decisions) for any fleet nested inside that star's system.
- `src/scene/GalacticViewScene.tsx` — galactic-view placeholder: starfield + "GALACTIC VIEW — Not yet charted" text, intentionally not built out further yet.
- `src/components/Breadcrumb.tsx` — top HUD nav, generic level labels only: GALAXY › INTERSTELLAR › SYSTEM › SATELLITE, clickable to jump up a level.
- `src/components/LockOnToggle.tsx` — top HUD button (next to `Breadcrumb`, inside a shared `.hud-top-right` flex group) toggling `viewStore.lockOnEnabled` — see Design Decisions.
- `src/components/LocationLabel.tsx` — the current *specific* location, e.g. "Sol System — Mars". Large and centered at the bottom of the screen (`.location-label`, absolutely positioned within `.hud-bottom`) — was originally a small subtitle under the app title; moved and enlarged since the location is core information the player should read at a glance (see Design Decisions).
- `src/components/TimeControls.tsx` — in-game date, pause/play, speed up/down, 5-pip speed indicator. Lives in the bottom-left HUD cluster alongside `ChatPlaceholder`, not centered (that spot is now `LocationLabel`'s).
- `src/components/ChatPlaceholder.tsx` — non-functional placeholder reserving a spot for a future fleet-comms/chat panel, bottom-left next to `TimeControls`.
- `src/components/Outliner.tsx` — collapsible right-side panel, Stellaris-style: a search box + kind-filter pills (Stars/Planets/Moons/Black Holes — the last one has no matching entries yet, reserved for when `GalacticViewScene` grows real content) above an "In View" section listing whatever the current view level shows (all stars in interstellar, Sol + all planets in system, the primary body + its moons in satellite — derived purely from `viewStore` + the same static data files every scene reads, colored dot/ring icons matching each body's real color) plus a real "Fleets" section (colored by `ALLEGIANCE_COLORS`, triangle icon matching the viewport) and placeholder "Colonies"/"Starbases" sections (empty — no gameplay systems back these yet, same non-invented-data spirit as `ChatPlaceholder`). Every section (including "In View") is independently collapsible via its own caret, on top of the whole panel's own collapse-to-edge-tab. Search/filter apply globally. **Entries are clickable** — "In View" entries call `viewStore.selectInView`, fleet entries call `shipStore.selectShip`, both highlighted (`.selected`) when active — see Design Decisions.
- `src/components/NavBar.tsx` — collapsible left-side nation nav, structurally the mirror image of `Outliner` (same collapse-to-edge-tab pattern, flipped): a hardcoded nation name ("Imperial State of Mars" — no empire/player system exists yet) and Stellaris-style category buttons (Situations/Government/Technology/Society/Species/Contacts/Fleet Management), each opening a `DraggableWindow` placeholder ("Not yet available") — same non-invented-data spirit as everything else placeholder in this HUD.
- `src/components/DraggableWindow.tsx` — generic movable HUD window (pointer-based title-bar drag, no resize) — currently used only by `InspectPanel`, but written generic in case other floating panels are wanted later.
- `src/components/InspectPanel.tsx` — the shared "inspect a body" window used by every view (system, satellite, and — via a plain `DraggableWindow` with the same row markup — interstellar too): wraps `DraggableWindow`, renders an `InspectableBody`'s basic info (type/radius/orbit/moon count) plus, for planets/moons, the `bodyStats.ts`-derived game info (size class, districts, habitability). Stars skip the game-info section (doesn't apply to them yet). Optional `action` prop (`{label, pendingLabel, pending, onClick}`) renders a "Detailed View"/"Enter System"-style button (or, while `pending`, a status line).

# Design Decisions Made So Far:
- **True-to-scale solar system**: orbital distances and body radii both use the *same* real-world scale factor (1 AU = `UNITS_PER_AU` scene units, currently 20), so relative proportions are physically accurate.
  - Tradeoff: at true scale, planet spheres are geometrically sub-pixel at any usable zoom. Fixed DEFCON-style: each body has a small constant-screen-size marker (circle + label, via drei `Html`) at its exact true 3D position.
- **Orbital tilts are real, not decorative**: real J2000 inclination + longitude of ascending node values, via `orbitMath.getOrbitPosition`.

  - **Mechanism**: `MoveOrder` gained three optional fields — `warpEngageSimDays` (when a two-phase order actually switches from reaction to warp speed), `warpEngageFraction` (the *distance* fraction, not time fraction, already covered at that switch — stored directly since the two phases move at very different rates, cheaper than re-deriving it in the render path), and `gravityWellClearSimDays` (present purely for status-line text, distinct from a cooldown wait even though both resolve through the same `warpEngageSimDays` gate). `getShipRenderPosition` now interpolates each phase on its own local timeline when these are set, falling back to the original single-span lerp when they're not (a plain reaction-only or plain full-warp order never sets them).
  - **Direction-change stop-and-start**: a new `isShipCurrentlyWarping(ship, simDays)` helper (true once `simDays >= order.warpEngageSimDays`, or immediately for a single-phase warp order) is checked first in `planMove`, before anything else — redirecting a ship actually mid-warp-leg forces `warpReadySimDays = simDays + cooldownDays` *right now*, returned via a new `warpReadyOverride` field on the `'order'` `MoveResult` (parallel to `'instant'`'s existing `hyperdriveReadySimDays`) and applied atomically by `shipStore.setShipOrder`'s new optional third param — no frame where the old order is gone but the penalty isn't in effect.   - **"Use Warp Drive" / "Warp When Ready"**: two new persistent `ShipInstance` booleans (`warpEnabled`, default `true` — preserves old behavior unless turned off; `warpWhenReady`, default `false` — an opt-in), toggled via two checkboxes in `ShipPanel` (gated on `hasWarp && owned`, same ownership gate as commanding at all) and new `shipStore.setWarpEnabled`/`setWarpWhenReady` actions. `warpEnabled` false always short-circuits to a pure reaction-drive order, full stop — no gravity-well/cooldown logic even runs. `warpWhenReady` only gates whether a *cooldown* wait mid-flight is worth taking (if false, cooldown-blocked trips just ride reaction the whole way, same fallback this project already had before warp had a cooldown) — it never gates the gravity-well wait, which is mandatory physics, not a timing preference.

The actual physical quantity used is **escape velocity** (`v = sqrt(2GM/r)`, computed at the body's real surface) rather than surface gravity — the more physically apt "how hard is this well to climb out of," and a fixed, real property of the body alone, independent of the fictional radius a ship's orbit is actually drawn at (`SYSTEM_SHIP_ORBIT_RADIUS`). `gravityWellEscapeDays(massKg, radiusKm) = EARTH_GRAVITY_WELL_ESCAPE_DAYS * (v_body / v_earth)` — only the *ratio* to Earth's own escape velocity is physically grounded; the `EARTH_GRAVITY_WELL_ESCAPE_DAYS = 1` anchor itself is still a picked, not derived, baseline (same "real constants, heuristic time mapping" pattern as `REACTION_DRIVE_SPEED_KM_S`/`LY_IN_KM`). Every call site that already queues on `'on-cooldown'` (`InterstellarScene.handleOrderToStar`, `useShipOrderSettler`'s follow-recompute branch) now also queues on `'paused'`, via `setPendingHyperdriveJump` exactly as before — from the caller's point of view the two `MoveResult` kinds are handled identically. `useShipOrderSettler`'s firing condition (`ship.pendingHyperdriveJump && simDays >= ship.hyperdriveReadySimDays`) gained an explicit `&& !paused` — provably redundant for a *real* tick (ticking itself requires `!paused`, so `settle()` can never observe `paused === true` from a genuine simDays change) but not for this hook's own mount-time `settle()` call, which runs once regardless of pause state; made explicit rather than relying on that reasoning holding forever. `getShipStatusText`'s queued-jump branch now also distinguishes *why* it's queued: `"queued — resume time to jump"` while paused (no numeric cooldown shown, since it isn't counting down and a stray `"0.0d"` would misleadingly suggest firing was imminent) vs. the existing `"queued (Xd)"` while genuinely waiting out the drive's cooldown. Verified via a pure-function test end-to-end: paused → ordered a jump → got `{kind:'paused'}` → queued it manually the way the real call sites do → confirmed the status text read `"Jump to Sirius queued — resume time to jump"` → unpaused → re-ran `planMove` for the same queued star and got `{kind:'instant'}` (a Turing Scout, 0% loss, for a clean deterministic check) — matches "queue it, then travel there instantaneously once time resumes" exactly as asked. Live UI verification of the right-click-while-paused path itself was blocked by the WebGL context-loss artifact (star markers only exist in Interstellar view, which was the 2nd Canvas mounted in the tab available at the time) — the underlying mechanism is proven by the pure-function test above, and every calling pattern involved (queue-on-`'on-cooldown'`, fire-from-`useShipOrderSettler`) was already separately verified live for the hyperdrive-cooldown case earlier this session.

## Combat system (Phase 1 — mechanics)

Built to an explicit four-part brief: a tactical time mode, per-component healthbars, a combat "detailed view" with a 3D movement grid, and a visible combat state. Scoped into three phases at the user's direction (mechanics → view → fleet UI) because the whole thing is several sessions of work; this section covers Phase 1, which is where the design risk actually sits.

- **Tactical time is a second *rate* on the existing clock, not a second clock.** Every position in this project is already a pure function of `simDays`, so `'tactical'` mode simply swaps `NORMAL_DAYS_PER_SECOND` (6) for `TACTICAL_DAYS_PER_SECOND` (1/86400 — one simulated *second* per real second). Nothing in the existing physics needed to change, and there is no parallel timeline that could desync from the strategic one. Speed tiers differ per mode (`[1,2,3]` tactical vs `[1,2,3,4,5]` normal — past 3x, individual shots land faster than they can be read); `setMode` clamps `speedIndex` into the new mode's range. The two paces differ by ~518,400x, which is exactly why the mode button (`.time-mode-btn`, STRAT/TAC) is styled far louder than the speed buttons beside it — it is not a neighbor of "one step faster." Tactical mode also shows a wall clock next to the date (`formatClockTime`), because at that pace the date is effectively frozen and the HUD would otherwise give no sign that time is moving at all.
- **The clock follows combat automatically, in both directions.** At normal 1x a real second is ~518,400 sim-seconds, so an entire battle resolves between two frames — combat is *literally* unobservable unless the game drops into tactical. So `useCombatResolver` pulls the clock down to tactical the moment an engagement forms, and hands it back to strategic when the last one ends. Both are gated on one preference (`combatStore.autoTacticalOnEngage`, default on) so it only ever undoes something it itself did, and neither touches `paused` — if you were paused when a fight broke out, you stay paused and get to look around first. Leaving out the return leg was a real bug caught in live testing: it strands the player at ~500,000x slower than strategic pace after every battle, which reads as the game having frozen.
- **Damage resolves through three layers with a per-weapon multiplier matrix** (`combatData.DAMAGE_PROFILES`), following the Stellaris convention the brief referenced. Energy is soaked by shields (0.5x) and melts armor (1.5x); kinetic is the exact mirror (1.5x / 0.5x). *The brief as written described both energy and kinetic as strong-vs-armor, which is the same thing twice — flagged and corrected to the mirror before implementing.* Missiles and torpedoes bypass shields outright and are instead answerable to point defense, a per-hull intercept chance rolled before any layer is touched — without it, torpedo boats are strictly dominant.
  - **Layer overflow is carried in *raw* (pre-multiplier) damage, not post-multiplier damage.** This is the subtle part: if a kinetic round overkills a shield and the surplus carried through at its 1.5x shield bonus, it would hit armor at 1.5x too, where it is supposed to be at 0.5x. Converting back to raw at each boundary (`applied / profile.shields`) is what makes the counter-matrix behave correctly on *partially* stripped layers rather than only on full ones. Directly regression-tested.
- **Three components, degrade-don't-instakill; only the core is lethal.** `weapons` scales firepower linearly (0 = can't shoot), `utility` scales thrust *and* FTL charge rate (0 = stranded and unable to flee), `core` at 0 destroys the ship. Disabling weapons or utility is never lethal by itself but can completely decide a fight, which is the whole reason for splitting them out. Damage that reaches this layer lands on the *targeted* component if one is chosen, otherwise on a random surviving component weighted by size, so a big core soaks proportionally more stray fire without any component being immune.
- **The overall bar blends all five pools, not just the three components.** First cut weighted only the components, reasoning that shields and armor are consumable buffers rather than the ship itself. Verification immediately showed why that reads wrong: a Battleship that won a fight having lost *every* point of shielding and half its armor still displayed 100% integrity. The brief said "a mixture of everything," and it was right to. Core still dominates (0.35), and weights are renormalized over whichever pools a hull actually has, so a shieldless design isn't permanently capped below 100%.
- **Persistent damage lives on `ShipInstance.combat`; everything transient lives on the engagement.** Component/shield/armor HP outlive a battle (armor never regenerates in the field — no repair system exists yet), while arena position, weapon cooldown timers, and chosen targets exist only for the duration of a fight and are stored on `combatStore.CombatParticipant`. A ship that disengages simply stops appearing in any engagement rather than needing a pile of arena fields reset on it.
- **Engagements form automatically on hostile co-location**, keyed by resting location (`combatLocationKey`). Only *resting* ships can meet: a ship mid-order is crossing real interplanetary distance and isn't anywhere another fleet could be sitting. Bare system/interstellar points are excluded too — matching two arbitrary float coordinates says "these ships share a float," not "these fleets met." Neutrals are genuinely inert (a real allegiance a fleet can hold without being dragged into every passing firefight); friendlies count as player-side.
- **Fleet-vs-fleet from day one, not 1v1.** The brief initially framed combat as duels, then correctly noted that pure 1v1 between empires isn't realistic. Sides are arrays of participants with free targeting, so N-vs-N works now rather than being a later rewrite of a duel abstraction.
- **The arena is a fixed-size cube subdivided into a lattice; ships travel its edges, including diagonals.** Arena span is constant (`ARENA_SPAN_UNITS = 12`) and only the subdivision count varies with density (`coarse`/`standard`/`fine` = 4/8/12), so a weapon's range in arena units means the same thing at every setting — density is a movement-resolution choice, not a rescaling. Diagonal hops need no separate cost rule: a body diagonal is physically √3 longer than a face hop, so deriving traversal time from distance charges for it automatically. Note weapons fire across *euclidean* distance while ships must travel the *lattice* — that asymmetry is deliberate and is what makes cutting a diagonal worth doing.
- **FTL charge is the only way out of a fight, and it costs you your guns.** A ship in an engagement is pinned — it can't leave at reaction drive. Ordering it somewhere instead begins a drive spool (hyperdrive 5s, warp 10s per the brief) during which it *cannot fire*, handing the enemy a real window to stop it. Charge time is divided by utility effectiveness, so a half-wrecked utility array doubles the spool and a dead one makes escape impossible — which is what makes utility a genuinely decisive target rather than a consolation prize. Implemented as a new `'engaged'` `MoveResult` returned from `planMove` *before* any drive logic, at the same single chokepoint that already enforces ownership, so no call site can bypass it and teleport a ship out of a battle.
- **A baseline approach behavior was necessary for Phase 1 to work at all.** Both fleets start on opposite faces 12 units apart — outside every weapon's reach — so with player movement deferred to Phase 2 a battle could never actually join; live testing showed exactly this (two ships staring at each other at 100% health indefinitely). Ships with nothing queued now close to a standoff just *inside* their own longest range (`APPROACH_RANGE_FRACTION = 0.7`) rather than to contact, so a long-ranged hull keeps its reach advantage instead of throwing it away. It only runs when a ship has no path of its own queued, so player orders (Phase 2) will always win.
- **Combat steps at a fixed timestep, and the accumulator must be strict.** `stepEngagements` advances in whole `COMBAT_STEP_SECONDS` (0.1) increments so outcomes never depend on framerate. A first cut advanced the cursor to "now" whenever less than a full step remained, which billed a partial frame as a *complete* step — at 60fps in tactical mode only ~0.017 sim-seconds elapse per frame, so every per-step effect (shield regen most visibly, measured running ~4x fast) ran too quickly *and* varied with framerate, defeating the entire point. Leftover time below one step is now carried into the next frame. Caught by measuring live regen against the in-game clock; regression-tested.
- **The resolver is pure and store-free**, exactly like `shipPhysics.planMove` — it takes `(engagements, ships, simDays, rng)` and returns what changed, with the RNG injected so tests can seed it. This is the primary verification path for combat: the browser sandbox can't reliably render a second WebGL context (see below), so a seeded scratch suite covering the damage matrix, layer overflow, point-defense rates, lattice geometry, engagement formation, a full battle from opening positions, FTL charge/escape, and regen rate is what actually establishes correctness. The live browser confirmed the integration end-to-end (auto mode switch both ways, health bars, a Corvette and a Swift Courier each destroyed, correct kinetic-vs-shields behavior).
- **Warship presets are differentiated by matchup, not stat inflation.** Corvette (shield-heavy, short kinetic), Frigate (long missiles, no point defense), Destroyer (highest PD, mixed guns), Cruiser (all three direct-fire types, no hard counter), Battleship (torpedoes, slow). Every warship keeps a real FTL drive per the brief, which is also what makes charge-and-escape available to all of them. The four pre-combat civilian hulls share one unarmed `CIVILIAN_COMBAT_PROFILE` — `combat` is *required* on `ShipClass` rather than optional, so every damage path is total and nothing needs a null check; an unarmed ship is an empty `weapons` array, not a missing profile.

## Combat system (Phase 2 — the combat view)

- **Combat is a real `ViewLevel`, not a modal overlay.** It gets the breadcrumb, the scroll-out-to-leave gesture, and the scene-remount transition every other level already has — the brief called it "the *detailed view* version of two fighting ships," and satellite view is the existing precedent for what a detailed view is in this project. It sits *outside* the galactic→satellite zoom ladder though: you don't reach it by zooming in on anything, you enter it from a ship that's in a fight, and leaving it lands you in system view (where the battle is physically happening) since there's no "one level up." The breadcrumb hangs COMBAT off SYSTEM for the same reason, styled hot to match the tactical clock.
- **`combatEngagementId` lives in `viewStore`, not `combatStore`.** It's navigation state that has to move in lockstep with `level` — splitting "which view am I in" from "what is that view showing" across two stores is exactly how you end up with a combat level mounted with nothing to render. (`combatStore.viewedEngagementId` remains for non-navigational uses.)
- **Entering combat is offered, never forced.** A fight already yanks the clock into tactical on its own; also teleporting the player's camera into an arena would be one automatic disruption too many, and would make it impossible to keep watching something else while a fight resolves. So `ShipPanel` grows an "Enter Combat" button when the selected ship is engaged, and that's the only way in. The view *does* exit itself automatically when the engagement ends, since there's genuinely nothing left to render.
- **The lattice is drawn in three layers of decreasing subtlety**: the full interior grid (faint), the node points ships can occupy, and the arena's outer cage (brightest — it's the hard boundary of the fight). Interior opacity *scales down* as density rises (0.5/0.3/0.16): at `fine` there are 507 lines crossing the view and at a fixed opacity they read as fog rather than as a grid. All lines go into one `BufferGeometry` per layer, so the whole lattice is three draw calls regardless of density and there's no need to cull interior lines.
- **Node picking scores every node against the click ray rather than raycasting geometry.** A click ray passes *through* many nodes, so "what did they click" can't be answered by a hit test. Instead an invisible box catches the click and every node is scored by perpendicular distance to the ray, closest wins — which is what players actually expect from a 3D grid, and at 2,197 nodes worst case it's a trivial per-click loop instead of 2,197 raycast targets in the scene. The catcher is a real mesh with a zero-opacity material rather than `visible={false}`, because an invisible object is skipped by the raycaster entirely and would never receive the click at all.
- **Player movement orders latch (`CombatParticipant.holdPosition`).** Without the latch, the resolver's default approach behavior resumes the instant a player-ordered path finishes and marches the ship straight back at the enemy — which makes deliberate kiting (the entire reason to give a long-ranged hull a speed advantage) impossible to actually perform. Ordering a move sets the latch; a "Resume Auto" control clears it *and* drops the queued path, so resuming takes effect immediately rather than after the ship finishes walking somewhere it's no longer meant to go.
- **Every committed route is drawn, not just the selected ship's.** Seeing where the enemy is heading is precisely the information positioning is meant to be played on. It also makes the lattice constraint *visible*: a ship crossing diagonally visibly staircases rather than gliding, and without the path lines the grid may as well be decoration.
- **Arena markers carry their own integrity bar and an FTL badge.** In a fleet fight the whole point of the arena view is seeing at a glance which ships are nearly dead and which are about to escape, without clicking through each one. A ship spooling a drive is defenceless and leaving — the single most decision-relevant fact on screen — so it gets a pulsing badge rather than living only in a panel.
- **`CombatShipMarker` reads position from the store every frame instead of via props.** The resolver rewrites participant state constantly during a fight; threading that through React props would re-render every marker on every step. `useFrame` + `getState()` keeps markers mounted and just moves their group, and the only React subscription is on health rounded to whole percent.
- **`CombatPanel` is separate from `ShipPanel` by design.** `ShipPanel` is a per-ship *inspector* available at every view level; `CombatPanel` is a per-engagement *command* surface that only means anything inside the arena. It's also the one window with no close button (`DraggableWindow.onClose` became optional for it) — dismissing it would leave the player in an arena with no way to give orders.
- **Verification note:** the interaction tests here have to be run with the clock *paused*. An early pass appeared to show the density and focus-fire buttons reverting their state; they were working correctly — the engagement was simply ending mid-test and taking the panel with it. Freezing the clock first made every control verify cleanly, and click-to-move + auto-approach were then confirmed running simultaneously (a manually-ordered player ship walking its path while a hostile closed on its own).

## Combat system (Phase 3 — environment, the movable frame, and fleet UI)

- **The arena is a *window* onto an unbounded lattice, not a box the fight is sealed in.** Node coordinates are now absolute and unbounded; `Engagement.center` says which node the visible cube is centred on, and a Recenter control slides it. That directly answers "movement shouldn't be constrained to the cube": a ship can be walked across the system a window at a time, and the cube only ever bounds *what can be ordered in one go*, never where a ship may exist. The scene, not the arena module, applies the centring offset when rendering — which is what lets the window move without rewriting a single stored position.
- **Density changes now remap every coordinate instead of accepting a snap.** Changing subdivision count changes the physical spacing between nodes, so the same integer would mean somewhere else and the whole battle would visibly jump. Remapping preserves each node's *world position*, making a density switch purely a change of movement resolution. (Phase 2 deliberately accepted the jump as harmless; once a body occupied a fixed world position, it stopped being harmless.) **Correction (Phase 4): this claim was wrong in practice.** "Remapping" round-tripped a position through real coordinates and snapped to the *nearest node of the new spacing* — a real, visible jump whenever the original position wasn't already an exact multiple of that new spacing, which is the ordinary case, not an edge case. This read exactly like "ships teleport to the nearest intersection on every density change," because that's what it was doing. See Phase 4 below for the actual fix (storing real coordinates as ground truth, so there's nothing left to remap).
- **Celestial bodies are real terrain.** Whatever the fleets are orbiting is placed at the window centre as a `CombatObstacle` with a real radius, and it blocks both line of fire and movement. Two fleets on opposite sides of a star genuinely cannot engage until one comes around — verified live: two Cruisers at Sol traded *no damage at all* for ~8 seconds before one manoeuvred into a firing position. Body radii come from real `radiusKm` through a fourth-root compression against Earth (moon ≈ 0.9 units, Earth 1.2, Jupiter ≈ 2.2, Sol ≈ 3.9 against a 12-unit arena) — real radii span four orders of magnitude and are unusable directly. Only the relative sizes are physical; the absolute scale is picked, same honesty as `moonData.ts`'s orbit compression.
  - Line of fire is a **segment**-sphere test, not an infinite-line one, so a body *behind* the shooter never blocks. Checked once per firing ship rather than per mount, since it's a property of the geometry, not the weapon.
  - Moons of the primary are deliberately excluded — at real scale they're far outside a 12-unit arena, so including them would be inventing geometry rather than modelling it.
- **Pathing became real A\*, but only when it has to be.** The greedy straight-line walk is still used in open space (cheap, and exactly optimal there); A* runs only when a body actually sits on that straight route, so the common case pays nothing for the obstacle system existing. The approach AI also had to learn to seek *firing positions* rather than just close distance — it samples directions around the target and picks the nearest one with clear line of sight. Without that, two fleets either side of a star sit forever, each unable to shoot and each convinced it was already in position.
- **Two real bugs this pass, both found live rather than by the tests:**
  - **The window/pathing deadlock.** A* was bounded to the *display window*, so any ship outside it (via recentring or a density remap) had every neighbour out of bounds, found no route, and froze permanently — observed as two ships sitting at 100% health doing nothing. The search box is now derived from the path's own endpoints plus a margin sized to the widest body. The principle: **pathing is simulation, the window is a camera, and they must not be coupled.** The approach AI's window check was removed for the same reason.
  - **Truncated long routes.** `greedyPath`'s loop guard was sized to the old bounded cube (`divisions * 3`), which silently cut any route longer than one window once the lattice became unbounded, leaving ships short of where they were sent. The guard is now derived exactly: each hop closes every differing axis by one, so a trip takes precisely `max(|dx|,|dy|,|dz|)` hops.
- **Panel placement.** Every `DraggableWindow` opened at the same spot, so the combat view's order panel and the selected ship's inspector landed exactly on top of each other. Fixed with an `initialOffset` — computed from the viewport rather than hardcoded, because a fixed 300px shove pushed the panel entirely off-screen at ~520px wide, which is a worse bug than the overlap it was fixing.
- **Fleet Management is the first NavBar category with real content behind it**, replacing its placeholder. Three subtabs per the brief: **Fleet Manager** (every ship in service with live integrity and current action — the counterpart to the Outliner's flat list: this is where you read the *state* of a navy rather than navigate to one ship), **Ship Designer** (a read-only catalog of the preset hulls with full component/defense/mount breakdowns and, more usefully than raw DPS, the damage-type *matchups* each loadout brings — since the counter-matrix is what actually decides fights), and **Strategizer** (deliberately empty, reserved not invented, same spirit as the other placeholders). Editing isn't wired up because no resource or refit system exists to make a custom design mean anything yet — but the underlying data is already a per-hull list of independent mounts and defense values, so a designer that *builds* loadouts drops onto this same model rather than needing a rewrite.
- **Turing Scout hyperdrive cooldown 27 → 7 days** (`TURING_HYPERDRIVE_COOLDOWN_DAYS`). Named separately rather than inlined so its two advantages — jump-safety and fast recycling — read as one deliberate design idea about its navigational AI, in one place.

## Combat system (Phase 4 — position-model rewrite, right-click movement, engagement counting, FTL risk)

- **Ship/body/window positions are now real, continuous coordinates (`ArenaPoint`) — never lattice indices.** This is the core fix for a real bug: the previous model stored a ship's position AS a `GridNode` (an index into that density's lattice), and a density change "remapped" every stored index by round-tripping it through real coordinates and snapping to the *nearest node of the new spacing*. That snap is a real, visible jump whenever the original position wasn't already an exact multiple of the new spacing — which is the normal case, not an edge case, so switching Coarse→Fine (or back) read as ships "teleporting to the nearest intersection," exactly as reported. The fix removes the bug at the root rather than patching the remap: `CombatParticipant.position`/`hopFrom`/`path`, `CombatObstacle.position`, and `Engagement.center` are now all `ArenaPoint` (plain `{x,y,z}` in real arena units, density-independent). `combatStore.setDensity` is now a one-line field flip — nothing needs remapping, because nothing is stored in density-relative terms to begin with. The lattice (`GridNode`, `GRID_DIVISIONS`) still exists, but purely as an ephemeral planning aid: a real position is snapped to the nearest lattice node only at the moment a route needs to be computed, and the result is converted straight back to real waypoints that never move again.
- **"Nodes are simply a pathfinding tool"**, per the explicit ask — implemented as: `orderParticipantTo` first checks whether the *straight real-space segment* from current position to the requested destination is clear (`segmentClearsObstacles`); if so, the ship walks that exact line to that exact point, which can be anywhere — not snapped to any intersection, in Coarse or Standard or Fine. Only when that direct line is obstructed does it snap both ends to the lattice, route around the body with A*, and convert the result back to real waypoints — and even then, the *final* waypoint is overwritten with the exact requested destination rather than left at its lattice-snapped position, so only the detour itself is grid-quantized, not the resting place. (Documented as an approximation: the very last leg, from the final detour waypoint to the exact destination, isn't re-checked for clearance — acceptable since that waypoint sits within about half a grid cell of the destination, but not a rigorous guarantee against every obstacle geometry.)
- **Movement is right-click; left-click no longer does anything on the grid.** Left-click-drag is OrbitControls' own camera-rotate gesture — sharing the button with "issue a move order" made ordinary camera orbiting and commanding a ship fight over the same input, which is what the report of "recentering causes problems" traced back to. `CombatGrid`'s invisible click-catcher mesh moved from `onClick` to `onContextMenu` (with `e.nativeEvent.preventDefault()` to suppress the real browser context menu), matching targeting (right-click a hostile marker), which was already right-click and needed no change — the two never collide since they're different objects (grid mesh vs. marker). Also **dropped `nearestNodeToRay`'s node-snapping search entirely** in favor of reading the click event's own `e.point` directly (the exact 3D intersection with the click-catcher), which is both simpler and is itself half of what makes off-grid placement possible.
  - Verification note: confirming this live took real debugging. Synthetic `contextmenu` events dispatched as a plain DOM `MouseEvent` (the browser's native type for that event) were never picked up by react-three-fiber's raycaster, regardless of coordinates or preceding pointerdown/up — only dispatching `contextmenu` as a **`PointerEvent`** (matching r3f's internal pointer-event taxonomy, not the DOM spec's native event type) was recognized. Worth remembering for any future synthetic right-click testing in this sandbox.
- **`activeEnemyContacts`/`isActivelyEngaged`** (`combatResolution.ts`) answer "how many enemies is this ship *actually* fighting right now," distinct from "is this ship part of a battle" — a fleet fight can easily include ships sitting outside anyone's range or blocked by a body, present in the Engagement but not exchanging fire with anyone. Range check uses **either** ship's reach, not just the querying ship's — a longer-ranged ship kiting a short-ranged one counts as actively engaging it even though the target can't shoot back, which is exactly the situation that mechanic is supposed to create. Surfaced in `ShipPanel` as a new "Engaged Against" row (below "Engagement," which keeps meaning the broader "in combat at X"), working for a selected enemy ship exactly the same as an owned one, per the ask.
- **FTL risk now has two independent, documented-scope modifiers** (`combatData.ts`): a small **core-damage** bonus (`coreDamageRiskBonus`, capped at 0.15) applied **universally** — any hyperdrive jump a damaged ship ever attempts, in or out of combat — and a larger **active-engagement** bonus (`ACTIVE_ENGAGEMENT_RISK_BONUS = 0.2`) that only ever applies at one specific moment: an FTL escape charge completing while the ship has a live enemy contact. That second constraint isn't a policy choice bolted on top, it's structural: `planMove` already refuses to plan an *ordinary* jump for any ship currently in an Engagement (its `'engaged'` short-circuit forces the charge-and-escape path instead), so "actively engaged" and "issuing a normal jump" are mutually exclusive by construction — the engagement bonus can only ever reach the two new roll sites in `planMove`'s warp branches (see below), never the pre-existing ordinary hyperdrive path.
  - **Warp escape risk is a genuinely new mechanic, deliberately scoped to combat only.** Ordinary warp travel has never had any risk in this project, and that's preserved exactly: `warpEscapeLossChance` is only ever consulted when `planMove`'s new optional `riskContext` parameter is present, and the *only* caller that ever passes one is `useCombatResolver`'s FTL-charge-completion path. A plain player-issued warp order (every existing call site) passes nothing, so the new roll code doesn't execute at all — not "rolls and gets 0%," genuinely unreached. Regression-tested directly: a ship with its core almost fully destroyed, given 200 ordinary warp orders with no risk context, never once lost the roll.
  - `activelyEngaged` is computed once per `useCombatResolver` tick, **before** stepping — by the time a completed charge reaches `planMove`, `stepEngagements` has already dropped that ship from its engagement (it's leaving), so `planMove` itself can no longer see what it was fighting. A tick-start snapshot is a deliberate, documented approximation (steps are 0.1s, a tick catches up at most 4s), fine for a coarse modifier, not intended as a precise mechanic.
  - `ShipPanel`'s Jump Risk row now folds in both modifiers live and appends "(elevated)" when either is active; a new Warp Risk row appears only for warp-capable ships when the figure is actually nonzero (a permanent "Warp Risk: 0%" on every peaceful ship would be noise, not information).
- **Turing Scout hyperdrive cooldown**: 27 → 7 days (`TURING_HYPERDRIVE_COOLDOWN_DAYS`, `shipData.ts`) — named separately from the shared baseline so its two advantages (jump-safety via `lossChanceOverride`, and this) read as one deliberate idea about its navigational AI, not two unrelated tweaks.

## Combat system (Phase 5 — real motion physics, stances, and two position bugs)

- **`CombatParticipant` now stores position + velocity, not a hop.** This is the root-cause fix for the reported "*giving a ship a new command teleports it to the destination I previously commanded*". The old model set `position` to the current leg's ENDPOINT the instant that leg began — so `position` meant "where this hop ends", not "where the ship is". `orderParticipantTo` then read it as the ship's start point and marked the hop complete, snapping the ship visually onto the previous order's destination. Position and destination are now different things (`position`/`velocity`/`positionSimDays`), which makes that entire class of bug unrepresentable rather than merely fixed — `orderParticipantTo` no longer writes a position at all, it only sets `path`.
- **The same conflation caused the second reported glitch — "*the line showing where the ship is going disappears the moment I give a command*".** For the common unobstructed order the route is a single waypoint, and the first movement step consumed it immediately, emptying `path` while the ship was still flying. `CombatPathLine` now reads live participant state per frame and draws from where the ship actually *is* through the remaining waypoints, so the line shrinks as the ship closes and vanishes only on arrival. It also stays mounted and hides itself via `setDrawRange(0,0)`, so routes appearing/completing never remount anything.
- **Ships are now provably sub-light, and the code makes it hard to regress.** The reported problem was real and quantifiable: light crosses the Sun's diameter in ~4.6s, and the old fastest hull (1.6 units/s) crossed Sol's *rendered* 7.76-unit diameter in ~4.8s — 96% of light speed, on reaction drives. `ARENA_LIGHT_SPEED_UNITS_PER_SECOND` (combatArena.ts) now derives that anchor from real constants (Sol's true radius and *c*, against Sol's rendered radius), and every hull's speed is declared as a fraction of it via `hullMotion(lightDivisor, secondsToCruise)` rather than as a bare number. Nothing caught the old value because nothing expressed the relationship; now a light-speed hull would require literally writing `hullMotion(1, …)`. Crossing times run 18.6s (Corvette) to 60.4s (Battleship) against light's 4.6s.
  - Honest caveat on the scale: because body radii are fourth-root compressed, the arena has **no single consistent km-per-unit scale** — one unit is ~179,000 km measured against Sol but ~5,300 km measured against Earth. The light anchor is therefore defined against one specific body rather than pretending a global conversion exists, and is documented that way in `arenaBodyRadius`'s comment. Fully realistic reaction-drive speeds (0.01c) would put a single arena crossing at ~12 minutes, which isn't playable; "clearly sub-light and visibly slower than light across the star you're fighting beside" is the honest bar actually being met.
- **Real acceleration, from one rule.** `integrateMotion` steers the velocity *vector* toward a desired velocity under a single `accel * dt` budget. Starting, stopping, and turning all fall out of that one constraint — turning spends acceleration exactly like speeding up does, so a Battleship sweeps a wide arc while a Corvette pivots, with no special-case turn logic. Braking asks each step "how fast could I be going and still stop exactly on the final waypoint" (`v = √(2ad)`); intermediate waypoints deliberately skip it so a ship flies *through* the corners of a detour instead of halting at each one. Rendering extrapolates along the velocity vector between the resolver's 0.1s steps (clamped to two steps) so motion stays smooth rather than visibly updating 10×/second.
  - Consequence worth stating: fights are now substantially longer, since closing 12 units at sub-light speed takes tens of seconds rather than a handful. That's the intended trade, and it's why tactical time gained its upper speed tiers back (below).
- **Four auto-combat stances** (`CombatStance`, resolved by `stanceDestination`), set per ship in **Fleet Management → Strategizer** and stored on `ShipInstance` so a doctrine can be chosen *before* a fight and persists across engagements. `balanced` (the previous behavior, still default) holds just inside longest range; `swarm` drives all the way in to the *shortest* mount's range, the only distance a mixed loadout fires everything; `kite` holds the outer edge of longest range and actively backs off when crowded, with a tolerance band so it isn't re-planning every step; `stall` refuses the fight by putting the nearest body between itself and the enemy, breaking line of fire outright (and simply opening distance when there's no body to hide behind). A manual move order still overrides the stance for that fight via the existing `holdPosition` latch.
- **Yellow dashed engagement lines** (`CombatEngagementLine`) between every pair actively trading fire — drawn as straight segments *ignoring the movement lattice*, because this is a line of *fire* and shots already travel straight; drawing it on the grid would imply a constraint gunnery doesn't have. Pairs come from the same `activeEnemyContacts` used for the "Engaged Against" readout and for FTL risk, so what's drawn is exactly what the simulation counts as engaged — there's no second cosmetic definition that could drift.
- **Fleet Management window sizing.** The content declared `min-width: 460px` inside a `DraggableWindow` hardcoded to 240px, so the text spilled straight out of its own frame. `DraggableWindow` gained an opt-in `wide` variant (560px, capped against the viewport) and `max-width`/`box-sizing` guards; the content now fills its window rather than dictating a width the window doesn't have.
- **Time controls: five tactical tiers, and speed decoupled from pause.** Tactical went 3 → 5 tiers with the slowest deliberately unchanged at 1x (the pace combat is authored at) — the upper tiers earn their place back now that closing takes real time, for skipping the approach rather than watching the shooting. Separately, `speedUp` no longer force-unpauses as a side effect and `slowDown` is no longer disabled while paused: both directions work in either state and neither touches `paused`. Pips now show the *selected* speed even while paused (dimmed), since blanking them would hide the very thing that's now adjustable.

**Verification note (browser sandbox):** catching a mid-fight moment by polling proved unreliable here, because real wall-clock time keeps advancing between agent tool calls — fights repeatedly resolved before a poll landed. What worked was doing the whole play→wait→pause sequence *inside a single* `javascript_tool` call with explicit `setTimeout` timing. And confirming the engagement line actually rendered was done by briefly instrumenting its live vertex count onto `window` under `import.meta.env.DEV`, reading it (2 vertices = one segment for one engaged pair, matching the panel), then removing the probe — the same "use an unmissable direct signal, not an inferred one" lesson as the earlier orbit-ring false alarm.

## Combat system (Phase 6 — click picking, placement resolution, route-line legibility)

- **A click is a RAY, not a point — and the old code hid that instead of solving it.** Reported as: "clicking a node creates a pathfinder to the node, but the path only goes to that node from a certain perspective... it just looks like it until I change views." Exactly right, and worse than described. `CombatGrid`'s click-catcher was a solid box spanning the window and the handler used `e.point` — the raycast hit — as the destination. **A raycast against a box can only ever return a point on the box's surface**, so every order landed on the arena's outer shell at whatever spot happened to lie along the view ray. Shell point and intended target are collinear from the camera that issued the order, which is precisely why it looked right until the camera moved. Measured against the real geometry before touching anything: **all 729 standard-density nodes mis-picked, 729/729 landing on the shell, the worst by 19.81 units across a 12-unit arena** — the arena's entire interior was unreachable by right-click. Combat only kept working because the stances auto-approach; manual movement had been ordering ships to the wall since Phase 4.
  - Phase 4 introduced this. Its recorded reasoning — that dropping `nearestNodeToRay` in favour of `e.point` was "simpler, and half of what makes off-grid placement possible" — was wrong: it removed the only thing resolving depth, and the box silently supplied a garbage depth in its place. Noted here rather than left standing in the Phase 4 entry.
- **The lattice is what resolves the ambiguity, because its nodes are discrete points in 3D.** "Which node did the cursor land on" has a single answer where "how deep along this ray" has none. `pickLatticeNode` (combatArena.ts) projects candidate nodes to screen and takes the one nearest the cursor, with depth used *only* to break ties between nodes drawn on top of each other. Taken as a `project` callback rather than a camera, so it stays pure and unit-testable without mounting a scene — the same discipline as the rest of that module, and directly motivated by the fact that the bug it replaces lived in exactly the kind of untested scene code this project otherwise avoids.
  - **The ordering of those two criteria is load-bearing and was got wrong once mid-implementation.** The first version treated any node within a fixed 14px radius as "clicked" and ranked that whole band by depth — which let a node 13px away outrank the one the cursor was sitting exactly on, purely for being nearer the camera. Live measurement caught it: four of five clicks landed on a neighbour. Screen proximity now decides, and `tieRadius` (4px) only separates genuinely overlapping dots. That is a smaller version of the same failure as the shell bug — something other than where the player pointed deciding the answer — and it is why the live click test exists rather than trusting the unit tests alone.
  - **What remains ambiguous is genuinely irreducible**, and is documented as such rather than papered over: nodes that really do share a view ray cannot be told apart by one click. Front-most is the honest answer — it is the dot the player can see — and orbiting slightly breaks the alignment and exposes the rest. Measured live at 8/8 exact from the default camera and 5/6 from a second angle, the single miss being a provably collinear pair.
  - Nodes buried inside a body are excluded from picking. They are never legal destinations (`orderParticipantTo` refuses them), so including them would turn "click across the star" into an order that silently does nothing.
- **Placement resolution is the fine lattice, and the densities now nest to make that true.** Per the explicit ask: "the resolution is essentially the fine version of the grid — ships will always be on the intersection for fine mode, but not always for coarse or standard." Implemented as: a click resolves to a node actually *drawn* at the current density (the player can only aim at dots they can see), and `GRID_DIVISIONS` changed **fine 12 → 16** so the three densities are 4 | 8 | 16 — each exactly double the last. That nesting is a requirement, not a tidy coincidence: at the old 4/8/12, standard's 1.5-unit spacing has no counterpart on a 1.0-unit lattice, so ordering at standard density would have landed ships **up to 0.87 units off the dot that was clicked** — a milder replay of the very bug being fixed. Coarse and standard are untouched, so only the finest tier gained resolution (2197 → 4913 nodes, still one draw call).
  - Consequences, both intended: in fine view a ship always sits exactly on a drawn intersection; in coarse or standard view it frequently sits between them, because those densities don't draw every position a ship can occupy. It also gives the density control real weight for movement instead of leaving it cosmetic — coarse for quick chunky repositioning, fine for placing a hull exactly.
  - **Scope boundary worth stating:** this constrains what the *player can ask for*, not where a ship can be. `orderParticipantTo` is unchanged and still accepts any real point, and stance/auto-approach destinations are still continuous — so AI-moved ships are not lattice-aligned. The Phase 4/5 real-coordinate position model is fully intact; only the picker sits on top of it.
- **Route lines drawn with `Line2` instead of `lineSegments`.** WebGL ignores `linewidth` on `LineBasicMaterial`, so a route was stuck at one hardware pixel and read as just another strand of a lattice that already has hundreds of them. drei's `<Line>` builds segments as camera-facing quads, giving a real 2.6px width. The buffer is still written **in place** (Line2 interleaves both endpoints of each segment at stride 6, and `instanceCount` selects how much is live) rather than via `geometry.setPositions`, which reallocates on every call and would do so 60×/second per ship — preserving the no-reallocation property the previous implementation had.
- **Route lines now render only for player-owned and allied ships.** Hostiles and neutrals still manoeuvre exactly as before — this hides the *information*, not the behaviour. Knowing precisely where an enemy is heading several seconds early trivialises the positioning the fight is played on; reading their heading off the hulls is the intended skill. (Reverses Phase 2's "every committed route, not just the selected ship's", which had the opposite reasoning; the ask was explicit.)

**Verification note (browser sandbox) — the earlier synthetic-right-click note was incomplete and cost real time here.** Phase 4 recorded that r3f only recognises a synthetic `contextmenu` dispatched as a `PointerEvent`. True, but two further conditions matter and neither was written down:
  1. **Dispatch on `state.events.connected`, not the canvas.** r3f connects its listeners to a wrapper `<div>`, so events fired at the `<canvas>` are never seen. There is no `__r3f` on the canvas to discover this from — read `useThree().events.connected`.
  2. **`offsetX`/`offsetY` must be set explicitly, and a `pointerdown` must precede the `contextmenu`.** r3f's default `compute` reads `event.offsetX/offsetY`, which a synthetic event leaves at 0 (every click lands in the top-left corner); and click-type events only fire on objects that were in the hit list of a preceding pointerdown. The working sequence is `pointermove → pointerdown → pointerup → contextmenu`, all as `PointerEvent`s with `offsetX`/`offsetY` defined via `Object.defineProperty`.
Also confirmed again that batching many synthetic clicks into one `javascript_tool` call hits the 30s tool timeout well before it hits any app limit — ~8 clicks with 60ms settling is a comfortable ceiling per call.

## Combat system (Phase 7 — real-time AI tracking, real gravity, Flee stance, targeting UX, player-only fleet views)

- **Auto-controlled ships now re-track a moving stance destination every step, not just when idle.** Reported as: a kiting/swarming ship would commit to wherever its target was the INSTANT an order was queued and never reconsider — because the approach logic's guard was `if (p.path.length > 0) return p`, which conflated "has a route queued" with "is under manual control." Those are different things: a manual order and a stance-issued one both populate `path` identically, so the guard silently froze auto-piloted ships the same way it correctly protected a player's own order. Fixed by keying off `holdPosition` (the actual manual-control flag) instead, and recomputing `stanceDestination` every step regardless of whether a route already exists — replanning only when the fresh destination has moved more than `STANCE_REPLAN_TOLERANCE` (0.25 units) from where the existing route already ends, so a target holding still doesn't cost a fresh lattice plan every 0.1s step. Verified live in the resolver: a target relocated mid-flight pulls the route's endpoint with it; sub-tolerance jitter leaves the participant object completely untouched (same reference, not just "close enough").
- **Overshot sub-waypoints are now dropped instead of treated as sub-destinations.** Reported as: a ship would visibly reach its destination, then peel back AWAY from it to go tag a stale waypoint behind it. Root cause: every node in `path` was being treated as something the ship was *required* to touch, when only the LAST one ever was (nodes are a pathfinding aid — see the Phase 4 header). `pruneOvershotWaypoints` drops the next sub-node the moment the ship's current position is both closer to the final destination than that sub-node is AND the straight line onward is actually clear — applied to every route regardless of who queued it (manual or stance), every step, before approach logic runs.
- **A ship with dead utility now drifts on real, unmodified momentum — a real physics bug was found and fixed while building the collision consequence below.** `integrateMotion`'s final `if (velocity.length() > maxSpeed) velocity.setLength(maxSpeed)` clamp ran unconditionally, and at zero utility `maxSpeed` is *also* zero — so a "drifting" ship's velocity was being snapped to exactly zero on the very next 0.1s step, not preserved. The clamp now only runs inside the `budget > 0` (real thrust) branch; with no thrust at all, velocity is left completely untouched by steering. Caught by writing the collision test below and watching a ship that was supposed to be coasting toward a body stop dead at step 1.
- **Flying into a body is now fatal.** There was no collision consequence at all before this — `isPointBlocked` was only ever consulted during route *planning* (refusing a destination inside a body, routing around one in the way), never checked against where a ship actually ends up after a step. That's exactly the case a dead-utility ship exposes: nothing is steering it around anything any more. A post-movement check now destroys any ship whose new position falls inside an obstacle, applied via the same "zero the core" path a normal shot-kill uses (so it also correctly stops that ship firing the same step it collides).
- **Bodies now have real gravity, felt only by a ship with no thrust of its own** — the explicit design brief being "thrusters let ships treat it as flat space; with utility dead, gravity is what's left." A working ship (any `accel > 0`) is completely unaffected — gravity is applied only inside `integrateMotion`'s zero-thrust branch, right alongside the velocity-preservation fix above, so a dead-utility ship's drift now curves and accelerates instead of continuing in a straight line forever. `CombatObstacle` gained `surfaceGravityUnitsPerSecondSq`, derived per body from real mass/radius via the standard `g = GM/R²` surface-gravity formula, then compressed onto arena scale by the same "one honest anchor, real ratios preserved" method `arenaBodyRadius`/`ARENA_LIGHT_SPEED_UNITS_PER_SECOND` already use: Earth is anchored so a dead-thrust ship starting a couple of units out falls in within tens of real seconds (legible within one fight, not a 19-real-minute literal free-fall or an instant unavoidable trap), and every other body's arena gravity is that anchor scaled by its REAL surface-gravity ratio to Earth's — so Sol pulls ~28x harder and Luna ~1/6th as hard, matching reality exactly in relative terms. `gravitationalAcceleration` sums every obstacle's pull as a real vector (an Earth fight now has two gravity sources, Earth and Luna, both counted). Live-verified end to end through the real resolver: a ship starting 2 units past Earth's arena radius with a small sideways velocity curved — not fell straight in — and crashed 32.2 real seconds later.
- **New `flee` stance, and it's now the automatic fallback for any ship that can't fight back.** Runs from the CENTROID of every hostile in the fight, not just the nearest one (`fleeDestination`) — genuinely different from Kite, which only ever backs off the one ship it's tracking. `stanceDestination`'s old "unarmed hull behaves as if stalling" fallback now points at flee instead, and is also newly gated on a `weaponsOnline` flag computed from live weapons-component HP each step — so a fully-armed ship whose weapons get shot offline mid-fight *also* falls back to flee automatically, not just a hull with zero mounts (a spawn-time default alone could never satisfy that half of the ask, since weapons go offline mid-fight, not at spawn). Stall remains a deliberate, explicit CHOICE even for an unarmed ship (still useful for pure survival) — only the *other* stances get silently rerouted to flee when there's no working weapon to hold a firing line for.
- **Combat targeting UX**: right-clicking a Hostiles row in the Engagement panel now assigns that ship as the selected ship's target — the same gesture the arena's own markers already used, just reachable from the roster too (useful once a fleet fight has more ships than fit on screen at once). Right-clicking an ALREADY-targeted ship (marker or roster row) now clears it back to auto-targeting — a second way to reach what the panel's "Auto" button already did, addressing the report that there was "no way to remove a target" (there was, via that button, but the right-click toggle is the more discoverable path since it's the same gesture that set it).
- **Fleet Manager and the Outliner's Fleets list are now player-owned ships only.** Both previously listed every ship regardless of allegiance — the Strategizer tab already scoped itself to `allegiance === 'player'` (this is "my orders," not a sensor sweep), and the other two now match it for the same reason.
- **Earth's own combat arena now includes Luna as real terrain.** Moons are still deliberately excluded from combat obstacles in general (a real orbit radius — 60 Earth radii for Luna — is six times the 12-unit window's own span, so including one honestly would mean inventing geometry, not modelling it — see the Phase 3 note this doesn't change). Luna is the one explicit exception: close enough, relative to its primary, to be worth it anyway. Its position (`EARTH_MOON_OFFSET`) is a picked, documented compromise exactly like every body's *size* already is (`arenaBodyRadius`) — there's no honest way to fit a 72-unit separation in a 12-unit window — just applied to a position instead of a radius. `MoonRawData` gained an optional `massKg` (only Luna's entry sets it — no other moon currently reaches a combat arena, so no other entry needs to lie about having a real value).
- **Satellite view now renders bodies at genuinely different sizes.** Every inspected body (star or planet) previously rendered at one flat `PRIMARY_VISUAL_RADIUS = 3` constant regardless of its real size — Sol and Earth read as visually identical, which is exactly the reported bug. `satelliteVisualRadius` compresses real radius with the same fourth-root curve `arenaBodyRadius` already uses, anchored so Earth keeps its long-tuned value of 3 (every camera-distance constant in this scene was tuned against that number) — Sol comes out at 9 (the clamp ceiling), Mercury at ~2.36, Jupiter at ~5.46. The first implementation attempt also scaled the initial camera distance proportionally to each body's own radius, which was wrong in a way only caught by actually comparing two screenshots: proportional framing makes every body fill the same fraction of the screen by construction, which defeats the entire point (you can't SEE Sol is bigger than Earth if both are auto-zoomed to look identically sized). Fixed to a single FIXED camera position (`[0, 6, 27]`, sized to comfortably frame the largest clamped body) shared by every satellite view — confirmed live, Sol now visibly dwarfs Earth, which visibly dwarfs Mercury, all from the same vantage.
- **Settings tab**: new NavBar category with the first real display preference — Navigation Line Thickness (Thin/Medium/Thick, defaulting to Thin). Wired into both `CombatPathLine` and the new out-of-combat `NavigationLine`.
- **Navigation lines now apply outside combat too, and point somewhere.** `NavigationLine` (system/interstellar views) mirrors `CombatPathLine`'s reasoning — a ship's current order drawn from its live position to `order.endPosition`, player/allied ships only (same information-hiding rule as combat's route lines). Both route-line components also gained a chevron arrowhead at each leg's endpoint (`routeArrow.ts`'s `arrowWings`, a pure, camera-billboarded function shared by both, tested independently of any scene) — showing the direction of travel, not just where the line goes.
- **`DraggableWindow` gained a collapse toggle and viewport drag-clamping.** Collapse hides the body, keeping the title bar; since the window is centred on its position via `translate(calc(-50% + ...))` on BOTH axes, naively toggling the body would shrink the box toward its own vertical middle and visibly drop the title bar. Fixed by compensating `pos.y` by half the body's measured height in the same click handler that toggles `collapsed`, so the top edge — and the title bar sitting on it — doesn't move (confirmed live: 0.5px residual, from the 1px border removed in the collapsed state, otherwise an exact round-trip). Dragging is now clamped so a window's rendered box can never leave the viewport, stopping exactly at the border rather than being draggable off-screen — computed by diffing the proposed position against the window's own live `getBoundingClientRect()`, so it needs no knowledge of the CSS `left`/`top` percentages driving its base position.
- **The dev-only debug console is no longer text-selectable** (`user-select: none`) — it's an overlay, not document content.
- Confirmed, not changed: tactical time's speed tiers already run at literally 1x/2x/3x/4x/5x real time (`TACTICAL_DAYS_PER_SECOND` is exactly 1 sim-second per real second, and the multiplier applies directly on top) — this was asked for as if it might not already hold, but the math was already exact.

**Verification**: 173 pure-function checks (up from 120), typecheck clean, build clean, plus live browser verification of the harder-to-unit-test pieces — real-time stance tracking, collision death, gravity's actual fall trajectory and timing, satellite-view relative sizing (screenshots), the Engagement-panel targeting toggle, and the collapse-anchor fix — all driven through the real production code paths (spawn → syncEngagements → stepEngagements), not synthetic fixtures alone.

## Combat system (Phase 8 — strategy-time backlog, panel layout, hull separation, out-of-combat drift, disengagement, chaff)

- **Combat no longer runs at ~240x after a trip through strategic time.** Reported as "go into strategy time, then back to tactical, and the fleets are still fighting in strategy time." Root cause was a compounding, permanent debt: the resolver catches up at most `MAX_STEPS_PER_TICK * COMBAT_STEP_SECONDS` (4 sim-seconds) per tick — about **240 sim-seconds per real second at 60fps** — while strategic pace advances the clock **518,400 sim-seconds per real second**. Every real second spent in strategic time therefore bought roughly **36 real minutes** of hyperspeed catch-up, which kept burning down long after the clock returned to tactical. The fix (`combatCatchUpCursor`) DISCARDS backlog beyond one tick's reach instead of queueing it, so combat always resolves against the current moment and returning to tactical is immediately 1:1 again. Extracted as a pure function specifically so the bound is unit-testable rather than buried in a hook — the numbers above are asserted directly, including the 36-minute figure, so the regression stays legible.
  - Deliberately keeps the documented "fights resolve offscreen at their own maximum pace" behaviour intact; what changed is only that unsimulated time is skipped rather than owed. Time a fight was never stepped through simply didn't happen to it, which is the honest reading of "combat is unobservable at strategic pace" the whole module is built on.
- **The combat view's two panels are pinned to opposite screen edges** (`DraggableWindow`'s new `anchor` prop) — the engagement roster left, the selected ship's inspector right — instead of both hanging near the middle and covering the arena. Replaces the old viewport-derived horizontal gap helper entirely: the edges do the separating at any width, which the gap maths could never guarantee (it collapsed to zero on a narrow viewport). Anchored windows skip the `-50%` horizontal pull-back but keep vertical centring, so the collapse-anchoring fix from Phase 7 still holds for both.
- **Two hulls can no longer occupy the same point.** A post-movement separation pass pushes overlapping ships apart symmetrically along the line between them (`SHIP_SEPARATION_UNITS`, 0.45), with a fixed-axis fallback for the exactly-coincident case that has no line to push along. Done as a correction rather than by teaching steering to avoid squadmates, deliberately: every stance resolves its destination from the ENEMY's position, so a whole fleet legitimately wants the same spot, and encoding "avoid your allies" into that choice would fight the stance logic for control of the same value. Two passes, not iterate-to-convergence — a residual overlap in a dense pile-up is acceptable for what is a readability rule, not a rigid constraint.
- **Ships can now leave a fight by simply outrunning it** (`DISENGAGE_DISTANCE_UNITS`, 30 — beyond both the longest weapon and the arena window's own span). Previously the ONLY exit was an FTL charge, which a ship with wrecked utility cannot even attempt, so a Flee-stance ship could run forever without ever escaping. A disengaged ship is relocated to a `system-point`, which is what makes it stick: `combatLocationKey` returns null for that kind, so `syncEngagements` can never pull it back into the fight it just left (every other location kind would re-form the engagement on the very next tick). Confirmed live end-to-end — two unarmed couriers auto-fled (no weapons → Flee), broke contact, and ended up reading "In Sol System, Deep Space" with the combat view exiting on its own.
- **Unpowered hulls keep drifting under real gravity OUT of combat too** (`useShipDriftIntegrator`), not just inside the arena. Unlike the arena — whose body radii are fourth-root compressed, leaving no consistent km-per-unit scale — system view IS true-to-scale, so this uses **real Newtonian gravity with no invented anchor constant**: `systemGravityAcceleration` sums the star and every planet at their live positions. Sub-stepped (`MAX_SUBSTEP_DAYS`) because gravity is inverse-square and strategic pace would otherwise integrate it in 6-day leaps straight past a body. Falling into a star or planet destroys the ship, matching the arena's own collision rule.
  - **Two real bugs were found by actually running this rather than only unit-testing it**, both about seeding the drift, and both worth recording because the failure mode was silent and plausible-looking:
    1. **Seeding at heliocentric rest made wrecks spiral into the Sun.** A ship in Earth orbit is also travelling with Earth around the Sun at ~0.34 units/day; dropping that velocity means it no longer orbits anything. Measured: a hull stranded near Earth struck **Sol after 64 sim-days**. Fixed by inheriting the body's own orbital velocity (`bodyOrbitalVelocity`, central-differenced from its live position).
    2. **Placing a stranded hull where a fleeing one goes put it outside the body's gravity entirely.** A powered ship that runs is placed 1.5 units out, but Earth's Hill sphere is only ~0.2 units — seven times closer. A wreck left at 1.5 units wandered up to 34 units away because the Sun dominates completely out there. Powered and stranded disengagement now use different offsets (1.5 vs 0.08 units), and the stranded nudge (0.003 units/day) is sized to stay well under escape velocity at that offset (~0.013) — an earlier 0.05 value was nearly **twice** escape velocity, so the wreck simply left. With both fixed, a stranded hull stays inside 0.084 units of Earth and falls into it after ~13 sim-days.
  - Worth knowing for any future work here: what binds a ship to a planet is the **differential** field, not the net one. At 0.08 units the Sun pulls on the ship ~5x harder than Earth does, but pulls Earth almost identically, so the common part cancels — which is exactly what the Hill sphere measures. A test asserting on the raw net vector fails while the behaviour is correct; assert on `g(ship) - g(body)` instead.
- **Chaff** (`CHAFF_CHARGES` 2, `CHAFF_DURATION_SECONDS` 6, `CHAFF_MISS_CHANCE` 0.5). Implemented as a **miss chance on incoming fire**, not a damage reduction — the two play very differently: a damage tax is something an attacker out-scales, while a coin-flip per volley is what makes spending one of only two charges at the right moment a real decision. Rolled after point defense (so a missile must survive interception AND still find its target) and applied to every damage type, since it degrades aim rather than physically stopping a projectile. Charges do NOT regenerate, like armor. The AI spends its own charges on two health thresholds (0.7, then 0.4) rather than one, so it doesn't burn both at the same instant, and only while ACTIVELY engaged — chaff spent while nothing can shoot you is exactly the mistake a player wouldn't make. Deployment runs BEFORE the firing step so a burst answers the same volley it was deployed against, not the next one. Verified live: `2 left` → `Active 5.7s` → `Active 3.2s` → `1 left`, a real 6-second burst at tactical 1x, plus a 4,000-shot statistical check landing at exactly 50.0% misses.
- **Browser swipe-navigation can no longer eject the player from a running game.** `overscroll-behavior-x/y: none` on html/body/#root, plus `overscroll-behavior: contain` on every scrollable panel so a gesture that hits a panel's scroll end doesn't chain up to the page and become history back/forward. A fixed-viewport canvas game has no reason to ever hand a horizontal swipe to the browser.
- Confirmed, not changed: tactical time's tiers already run at literally 1x–5x real time — re-verified rather than adjusted.

**Verification note:** the app's stores are NOT reachable by `await import(...)` from the console — Vite hands the dynamic import a *separate module instance*, so spawns made that way never reach the running UI (it kept reporting "No fleets deployed"). Everything live here was driven through the real UI instead (the dev console's own spawn controls). Related: the game clock does not tick while the browser pane is backgrounded, so anything depending on `simDays` advancing needs the pane fronted.

## Combat system (Phase 9 — playing against the odds)

The ask was for more to do when a fight is going badly. An earlier cut of this pass misread it as counterplay *to* chaff and built a range falloff that switched chaff off as enemies closed — exactly backwards, since a losing ship is usually one with enemies closing on it. A comeback tool doesn't need its own counter. That falloff was reverted; what follows is the corrected direction.

- **Chaff's miss chance 0.5 → 0.75, flat at any range.** Three shots in four don't connect. At an even coin-flip, a two-charge six-second countermeasure was a rounding error on a multi-minute fight. Auto-deploys by default for every allegiance now too (`ShipInstance.chaffAutoDeploy`, default true — spent the instant it's worth it, same threshold logic the AI already had), with a checkbox in the panel for a player who wants to hold a charge for a specific moment instead.
- **Fleet-wide focus fire** (`setFleetTarget`, "Focus Fleet" in the engagement panel). One click points every ship the player commands at the same hostile; clicking the active one releases the whole fleet back to auto. This is the canonical answer to being outnumbered — each kill permanently removes that ship's damage from the fight, so concentrating fire is how a smaller force closes the gap — and doing it ship-by-ship put the most clicking on the player who could least afford the time.
- **Local-odds readout on every roster row** (`×2`, `×3`, red above 1) — how many enemies can actually shoot that hull *right now*, from the same `activeEnemyContacts` the engagement lines and FTL risk already use. Shown for both sides, since spotting an isolated *enemy* is half the same decision.
  - This exists to make **splitting the fleet** playable, which was the first thing asked for: if outnumbered overall, the winning line is to arrange local 1v1s rather than fight 2v4 at once. Verified that the underlying behaviour genuinely supports it — enemies pick targets by proximity (`nearestEnemy`), so with the player's two ships pulled far apart, four hostiles split cleanly 2/2 rather than blobbing onto one. The mechanic was already there; what was missing was any way to *see* the local balance, which is what this readout supplies.
- **Scuttle — the doomed-ship trade.** Detonates a hull that's going to die anyway, damaging hostiles within 3 units with linear falloff. Yield scales with **remaining core**, which is the whole tension: a healthy ship makes a far bigger bang but is also the one you'd rather keep, so the best payoff never coincides with the moment you most want to spend it, and a nearly-dead hull is a poor bomb (this stops it being a free finisher bolted onto every losing fight). Blast damage goes through shields then armor then core via `applyRawBlast` rather than `applyShot` — a reactor breach has no damage type for the matrix, nothing for point defense to intercept, and no firing solution for chaff to spoil. Hits only the opposing side, so it never punishes keeping a formation. Behind a two-step confirm in the UI, since it's the one irreversible action in that panel.
- **Point defense now scales with the target's own weapons-component health.** Kept from the earlier cut because it survives the reframing intact — it *is* an underdog tool. PD was previously a flat hull stat nothing could degrade, so a Destroyer's 0.55 interception held at full strength until the instant it died and missile/torpedo boats had no play against it at all. Point defense is gunnery, so it now dies with the gunnery array: Focus Fire → Weapons brings the screen down. Measured 55% → 28% at half weapons → **0%** with the array destroyed. That's a setup a torpedo boat can now create and previously could not.

**Verification note (browser sandbox):** the preview pane only advances animation frames when a screenshot forces a paint — between screenshots the clock doesn't tick and r3f `Html` markers never mount, so DOM queries read empty and it looks like nothing spawned. Interleave `computer{action:"screenshot"}` between steps when driving anything frame-dependent. (In addition to the Phase 8 note that `await import(...)` gets a *separate* module instance from the running app.)
