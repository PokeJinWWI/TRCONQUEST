TR: Conquest
# Overview:
"Terra Relicta: Conquest" is a web-based grand strategy game.

# Setting / Lore:
## FTL Travel
Two methods of faster-than-light travel exist:
- **Warp Drive** — uses "Exotic Matter," a form of matter found on certain planets with a higher mass-energy conversion rate than normal matter. Warp drives use exotic matter to warp and move space itself to travel.
- **Hyperdrive** — uses "Hyperium," extremely rare to find naturally but yields effectively infinite energy. Hyperium cannot be broken up/subdivided, so each ship equipped with a hyperdrive is extremely valuable. Hyperdrives use hyperium to access "hyperspace," a dimension outside the normal universe where time passes faster, allowing FTL travel. (Exact mechanics of hyperspace aren't important to nail down yet.)
- Both exotic matter and hyperium don't just power FTL drives — they also power the entire ship's systems and weapons.

## STL (sub-light) Travel
- STL warp drives tend to use **antimatter**, harvested via massive particle accelerators or extracted from locations with high "antimatter density."

## Timeline
- The game's campaign starts in the **year 2600**.

# Visual Style / UX Reference:
- The game should look like a tactical map, similar to **DEFCON** (see reference screenshots: minimalist neon vector map, arcs for missile/unit trajectories, glowing markers, DEFCON-style HUD/side panels).
- Scale/view structure (4 zoom levels, see View Levels below):
  - **Planet view**: close-up of a single planet.
  - **System view**: 2D-ish top-down (like DEFCON's flat world map).
  - **Interstellar view**: 3D, styled like an **Obsidian graph view** — nodes (nearby stars) connected by edges.
  - **Galactic view**: 3D, same graph style, zoomed out to galaxy scale (placeholder only so far).

# Tech Stack:
- **Vite + React + TypeScript** (scaffolded via `npm create vite@latest -- --template react-ts`).
- **three.js + @react-three/fiber + @react-three/drei** for 3D rendering — chosen because the interstellar/galaxy view needs true 3D navigation, and it also drives the in-system view. `OrbitControls` (via drei) handles camera drag/zoom/pan in every view.
- **zustand** for shared app state: `gameTimeStore` (simulation clock) and `viewStore` (navigation level).
- Dev server: `npm run dev` (Vite, port 5173). `.claude/launch.json` is configured so the Browser preview tool can launch it by name `trc-dev`.
- Build: `npm run build` (runs `tsc -b && vite build`) — verified passing. Type-check only: `npx tsc --noEmit`.

# Project Structure:
- `src/App.tsx` — app shell: mounts the global clock (`useGameClock`), renders the HUD bars (breadcrumb nav top, time controls bottom), and switches the active scene component based on `viewStore.level`.
- `src/App.css` — all HUD styling (bars, breadcrumb, time controls, markers, star info panel, galactic placeholder).
- `src/index.css` — minimal full-viewport dark reset.
- `src/state/gameTimeStore.ts` — zustand store for the simulation clock: `simDays` (elapsed since Jan 1, `START_YEAR` = 2600), `paused`, `speedIndex` (into `SPEED_MULTIPLIERS`, Stellaris-style discrete tiers), plus `tick`/`togglePause`/`speedUp`/`slowDown` actions. Helpers `simDaysToDate` / `simDaysToYears` convert sim time for display and orbit math.
- `src/hooks/useGameClock.ts` — drives `gameTimeStore.tick()` off a `requestAnimationFrame` loop mounted once in `App.tsx`, independent of any `<Canvas>` — so the clock survives view-level Canvas remounts.
- `src/state/viewStore.ts` — zustand store for navigation: `level: 'galactic'|'interstellar'|'system'|'planet'`, `selectedStarId`, `selectedPlanetName`, with `enterGalactic`/`enterInterstellar`/`enterSystem`/`enterPlanet` actions.
- `src/scene/orbitMath.ts` — shared helpers: `getOrbitPosition` (circular orbit position with inclination + ascending-node tilt applied), `angleForYear` (angle from simulated years + orbital period + phase), and `getPlanetPosition(data, simYears)` (a planet's exact live position from data alone — no component/ref needed, so the camera fly-to rig can independently compute where a planet is each frame).
- `src/scene/planetData.ts` — real astronomical data (AU distances, km radii, orbital periods, **inclination + longitude of ascending node** — real J2000 values, plus a fixed arbitrary **`phaseDeg`** starting position per planet) for the Sun + 8 planets, converted into scene units via a single unified scale (`UNITS_PER_AU`). `phaseDeg` is deterministic (not random) specifically so `getPlanetPosition` gives consistent answers to any caller.
- `src/scene/Sun.tsx`, `src/scene/Planet.tsx`, `src/scene/OrbitRing.tsx` — system-view scene components. `Planet.tsx` reads global sim time directly from `gameTimeStore.getState()` in `useFrame` (no local per-frame accumulation, so pause/speed changes apply instantly and consistently). Both `Sun` and `Planet` are marker-only (no visible sphere model at this zoom level — the Sun's mesh was removed so it's consistent with planets) and take a `selected`/`onSelect` prop rather than navigating directly on click (see the select/focus model below).
- `src/scene/CameraFocusRig.tsx` — reusable: each frame, lerps the camera + `OrbitControls.target` toward a live target position (`getTargetPosition()`, re-evaluated every frame so it can chase a moving planet), shrinking distance exponentially (frame-rate independent), and fires `onArrive` once within `arriveDistance`, while `OrbitControls` is disabled for the duration. Used for the one *animated, automatic* flight in the app: the "Detailed View" button's fly-in, and interstellar's fly-to-a-clicked-star.
- `src/scene/SelectionTracker.tsx` — reusable: every frame, *eases* `OrbitControls.target` toward a live object position (exponential smoothing, not an instant snap) while leaving user input **enabled** — this is the passive "camera lock" (object stays centered no matter how the player free-zooms/orbits from there), as opposed to `CameraFocusRig`'s automated flight. The continuous easing is what makes engaging the lock — or switching to a new target — pan smoothly from wherever the camera was already looking, rather than snapping. Runs at r3f priority `-2` so the target is fresh before drei's own OrbitControls update (priority `-1`) consumes it.
- `src/scene/DistanceThresholdWatcher.tsx` — reusable: fires once when camera distance crosses a min or max threshold. Distance is measured from the world origin by default, or from the current `OrbitControls.target` if a `controlsRef` is passed (needed so "zoom out to leave this view" still works correctly while camera-locked onto something off-origin, like Saturn). Drives *scroll-past-the-edge-to-navigate* between whole view levels: zoom out of planet view → system; zoom out of system → interstellar; zoom in on Sol in interstellar → system; zoom out of interstellar → galactic. Has a `graceMs` (default 500) after mount to absorb scroll-momentum carryover from the previous view (see Design Decisions).
- `src/utils/forwardWheel.ts` — `forwardWheelToCanvas`: the HTML marker overlays (drei `Html`) sit on top of the canvas and, since they need `pointer-events: auto` for click/hover, also swallow wheel events before they reach the canvas underneath (they're a DOM sibling of the canvas, not a descendant, so the event never bubbles there). This matters once a body is camera-locked — its marker sits right where the cursor naturally is while scrolling to zoom — so every marker's `onWheel` re-dispatches the event onto the actual `<canvas>` element. Found and fixed while testing the camera-lock feature.
- `src/scene/HologramPlanet.tsx` — the DEFCON/HUD-style planet visual used in planet view: a dark core sphere, a sparse lat/long wireframe grid, a glowing Fibonacci-distributed dot cloud, and a fresnel rim-glow shader (backside-rendered, additive blending) — all **procedural** (geometry + a small custom GLSL shader), no texture/image assets. Colored per-planet using `data.color`.
- `src/scene/SolarSystemScene.tsx` — system-view `<Canvas>` + wrapper div (for the info panel, a DOM sibling). Implements the **select = lock on immediately** model (see Design Decisions): local state `selectedName` (marker clicked → shows info panel *and* immediately engages the camera lock via `SelectionTracker`) and `flyingToName` (Detailed View's automated flight in progress, `CameraFocusRig` takes over from `SelectionTracker` for this). `onPointerMissed` on the Canvas clears selection (click empty space to unfocus). A `DistanceThresholdWatcher` (max, using `controlsRef` so it measures from wherever the camera is currently centered) fires `enterInterstellar` on zoom-out past the system's edge — active whenever not flying, *including while locked onto a planet*.
- `src/scene/PlanetViewScene.tsx` — planet-view `<Canvas>`: renders `HologramPlanet` for the selected planet (visual-only radius, not true-scale — this is a close-up), own OrbitControls, a `DistanceThresholdWatcher` (max) that fires `enterSystem` on zoom-out past the edge.
- `src/data/starData.ts` — real nearest-neighbor stars/systems to Sol (within ~10 ly: Alpha Centauri, Barnard's Star, Wolf 359, Lalande 21185, Sirius, Luyten 726-8, Ross 154), with Cartesian positions derived from real RA/Dec/distance. Only Sol has `hasSystemData: true` (drillable into system view) — others are informational only for now.
- `src/scene/InterstellarScene.tsx` — interstellar-view `<Canvas>` + wrapper: renders star nodes (Obsidian-graph style) as marker labels only — no sphere model, no connecting lines yet (those represent player-plotted routes, added later, not drawn automatically). Clicking a star flies the camera to it (`CameraFocusRig`) and shows the info panel; on arrival, `enterSystem` fires only if that star `hasSystemData` (currently just Sol) — otherwise the camera simply stops there with "No system data available" shown. `DistanceThresholdWatcher`s handle zoom-in-on-Sol → system and zoom-out → galactic (both only active while nothing is focused).
- `src/scene/GalacticViewScene.tsx` — galactic-view placeholder: starfield + "GALACTIC VIEW — Not yet charted" text, intentionally not built out further yet.
- `src/components/Breadcrumb.tsx` — top HUD nav, generic level labels only: GALAXY › INTERSTELLAR › SYSTEM › PLANET (no star/planet names in the crumb itself), clickable to jump up a level (zoom out).
- `src/components/LocationLabel.tsx` — small subtitle under the app title (system/planet levels only) showing the *specific* location, e.g. "Sol System" or "Sol System — Mars" — this is where the specific name lives now that the breadcrumb is generic.
- `src/components/TimeControls.tsx` — bottom-center HUD: current in-game date (Stellaris-style "D MON YYYY"), pause/play toggle, speed up/down, 5-pip speed indicator. (The old bottom-left "drag/scroll/pan" control hint text was removed — a tutorial will cover controls later.)

# Design Decisions Made So Far:
- **True-to-scale solar system**: orbital distances and body radii both use the *same* real-world scale factor (1 AU = `UNITS_PER_AU` scene units, currently 20), so relative proportions are physically accurate — e.g. inner planets genuinely cluster tightly near the Sun while Neptune sits far out (~601 units vs Mercury's ~7.7 units).
  - Tradeoff: at true scale, planet spheres (especially Mercury/Venus/Earth/Mars) are geometrically sub-pixel at any usable zoom. Fixed this DEFCON-style: each body has a small constant-screen-size marker (circle + label, via drei `Html`) rendered at its exact true 3D position, so it stays visible/legible/clickable at any zoom level regardless of true geometric size. The real-scale sphere mesh is still there underneath for when the camera gets close enough to see actual geometry.
  - Because of the real scale's huge range (~780x from Mercury's orbit to Neptune's), scrolling from a close-in view to the full system takes many scroll ticks — physically honest but can feel slow; click-a-planet-to-zoom (now implemented via planet view) is the mitigation.
- **Orbital tilts are real, not decorative**: each planet's inclination and longitude of ascending node use real J2000 values, applied via `orbitMath.getOrbitPosition` (rotate about X by inclination, then about Y by ascending node). Verified visually — from an edge-on camera angle the 8 orbits show slight vertical spread rather than a single flat line, matching the real (small, a few degrees at most) solar-system tilts.
- **Global time engine (Stellaris-style)**: single `gameTimeStore` holds `simDays` since 2600-01-01, advanced by a `requestAnimationFrame` loop (`useGameClock`, mounted at the App level, not inside any Canvas) so it's unaffected by view-switching remounts. 5 discrete speed tiers + pause, matching Stellaris' UX. All orbital motion (planets so far; stars/ships/galaxy later) is a **pure function of `simDays`** (via `angleForYear`) rather than per-frame delta accumulation — this means pausing/speeding up is instant and can't drift or desync between bodies.
- **View levels as separate `<Canvas>` per level**: galactic/interstellar/system/planet each mount their own Canvas rather than sharing one camera rig. Simpler to build/reason about; the cost is a brief remount on transition, judged acceptable since switching levels is an infrequent, deliberate user action (not per-frame).
  - **Gotcha learned the hard way**: each remount creates a new WebGL context. Heavy back-and-forth navigation within one browser tab (e.g. rapid testing) can accumulate enough contexts to hit the browser's limit, causing `THREE.WebGLRenderer: Context Lost` and a frozen/stalled scene. Fix in that situation is a hard tab reload (or new tab) — not a code bug, but worth knowing if a scene ever appears to "freeze" after lots of navigation. If this becomes a real problem during normal play (not just dev testing), the fix would be moving to a single shared Canvas/context — noted as a possible future refactor, not done yet.
- **In system view: select = lock on immediately, not click-to-jump.** Clicking a planet or the Sun both selects it (shows a general-info panel with a "Detailed View" button for planets) *and* immediately engages the camera lock (`SelectionTracker`, smoothly easing the target from wherever the camera was already pointed) — it does **not** change zoom level or view level by itself, and does **not** require zooming in first (an earlier version gated the lock behind "the player zooms in," which per feedback should never have been required — lock-on should happen the instant you click). From there: zooming in/out/orbiting freely still works, staying in system view (the lock only re-centers the target, never moves the camera itself), and zooming out far enough still exits to interstellar exactly as if nothing were locked (see the `controlsRef`-aware `DistanceThresholdWatcher` above — this was a real bug: it used to be disabled entirely while tracking). Clicking "Detailed View" (planets only, no such view exists for the Sun yet) triggers the automated `CameraFocusRig` flight and, on arrival, transitions into planet view. Clicking empty space (`onPointerMissed` on the Canvas) clears the selection/lock.
- **Interstellar view still flies on click** (not select-first) — clicking any star immediately sends the camera toward it via `CameraFocusRig`; only Sol transitions into a system on arrival. This is intentionally *not* unified with system view's select-first model yet — the request that prompted the system-view redesign was scoped to system view specifically. Worth revisiting for consistency later.
- **Scroll-past-the-edge navigation between whole levels** (separate from the above): `DistanceThresholdWatcher` fires a level transition when the user scrolls out past a view's outer edge or in past Sol's position in interstellar view. Wired both directions for every adjacent pair: planet↔system↔interstellar↔galactic.
- **Every scene swap gets a CSS fade/scale-in** (`.view-transition` in `App.tsx`, keyed by location) regardless of what triggered it (click, scroll-past-edge, or breadcrumb), so navigation always reads as smooth rather than a hard cut.
- **Interstellar view uses real star data, no connecting lines yet**: nearest real stars/systems to Sol within ~10 ly, positioned via actual RA/Dec/distance converted to Cartesian (see `starData.ts`). Only Sol is drillable into a system view; other stars are clickable (camera flies to them, info panel shows) but don't drill down since there's no system data for them. The hub-and-spoke lines from an earlier iteration were removed — those represent routes the player plots later, not something drawn automatically.
- **Galactic view is intentionally a stub** per explicit instruction — starfield + placeholder text only, reachable from the breadcrumb or by zooming out past interstellar, nothing else built.
- **Celestial body visuals are procedural, not textured**: the DEFCON/HUD "hologram" look (wireframe grid + glowing dot cloud + fresnel rim glow, see `HologramPlanet.tsx`) is built entirely from Three.js geometry + a small custom shader — deliberately chosen over raster textures both because it matches the game's vector-art DEFCON aesthetic better than photographic surface maps would, and because no texture assets were available. An `assets/` folder exists at the project root for future binary assets (the user's own convention: create a subfolder per asset type before adding files, e.g. `assets/planets/`) — nothing has been placed there yet. If real surface textures are wanted later (e.g. actual photographic planet maps), they'd go in `assets/<subfolder>/` and get wired into `HologramPlanet`'s core material.
- **Marker/orbit line colors are bright cyan** (`#2fd8ff` for orbit rings) — an earlier dim navy (`#1c3a5e`) was too hard to see against the black background.
- **Markers have `user-select: none`**: without it, a real mouse click with any cursor jitter between mousedown/mouseup (extremely common, unlike a perfectly still automated click) gets hijacked by the browser into a native text-selection drag over the marker label instead of registering as a click — showed an ugly highlight. Fixed on `.planet-marker` in `App.css`. Worth remembering for any other future clickable-text HUD element.
- **`onPointerMissed` race with marker clicks (the real cause of "selection doesn't work" after this)**: r3f's `<Canvas onPointerMissed>` fires for *any* click inside the canvas's shared event container that doesn't raycast-hit a 3D object — and drei's `Html` markers are portaled into that same shared container (so they can render above the canvas), not into the canvas itself. So clicking a marker fires two things almost simultaneously: the marker's own `onClick` (selects it) *and* r3f's `onPointerMissed` (since the click didn't hit any actual mesh — our planet meshes are true-scale/invisible) — and the miss handler cleared the selection that was just set, in the same tick. Fixed in `SolarSystemScene.handleUnfocus` by checking `event.target.closest('.planet-marker')` and ignoring the miss when the click actually landed on a marker. Root-caused by adding temporary event logging (`onPointerDown`/`onClick` on the marker, plus a log in `handleSelect`/`handleUnfocus`) and watching the console order — `handleSelect` fired, then `handleUnfocus` fired right after and won. Worth remembering: **any** future `onPointerMissed` usage in this app needs the same guard, since all HTML overlay markers share this failure mode.
- **`CameraFocusRig` snaps its target exactly each frame, never lerps it**: an earlier version did `controls.target.lerp(liveTargetPosition, t)` — a *partial* catch-up per frame — which left the target perpetually lagging a moving planet (steady-state lag ≈ orbital tangential speed / rig speed). Since arrival is judged against the *true* live position, not the lagged target, a fast-enough-orbiting or high-game-speed planet's lag could stay ≥ `arriveDistance` forever, so "Detailed View" would never actually complete while time was running (worked fine paused, since a stationary target has no lag). Fixed by copying the live position straight into `controls.target` every frame and only easing the camera's *distance* from it — the "flying in" look comes entirely from the distance animation now, not from a target catch-up. Verified fixed with real time running (not paused).
- **Marker dot must be centered independently of the label, not the whole marker row**: `.planet-marker` used `transform: translate(-50%, -50%)` on the flex row containing *both* the dot and the label — which centers the row's overall bounding box on the anchor point, not the dot specifically. Since the label extends further than the dot, the dot itself ended up visibly offset from the anchor (and therefore off the orbit ring, even though the underlying orbit math is identical between `Planet.tsx`'s position and `OrbitRing`'s points). Fixed by switching `.planet-marker` to `position: relative` with the dot absolutely positioned and centered via its own `translate(-50%, -50%)`, and the label absolutely positioned to its right — so the dot always sits exactly on the true point regardless of label width.
- **`DistanceThresholdWatcher` has a `graceMs` (default 500) after mount** before it will fire: scroll/trackpad momentum can carry a few extra wheel ticks past the moment a level transition fires, and since that lands on a *freshly mounted* Canvas with its own default camera distance, those leftover ticks could immediately trigger *another* level transition the player never intended (e.g. planet→system→interstellar from one continuous zoom-out gesture). Verified the fix holds even under an artificially extreme 150-tick synchronous burst (far more aggressive than real scroll momentum) — it now stops cleanly at the first transition instead of cascading.
- **Exit thresholds are tuned so the current view shrinks to "basically a dot" before handing off**, not just a modest zoom-out: system view's exit-to-interstellar threshold is `26000` units, interstellar's exit-to-galactic is `3500`. Verified visually: right before the system-view transition, the whole system (all planet markers + orbit rings) has visually collapsed into a single indistinguishable point at Sol's marker. The tradeoff is that reaching the threshold by scrolling takes real, deliberate zooming out (dozens of ticks, multiplicative ~5%/tick) — treated as intentional/acceptable here since "it should feel like actually pulling back out of the system" was the explicit ask, not a quick couple of clicks.
- **`SelectionTracker` eases continuously rather than snapping** (see above) specifically so lock-on-by-click feels smooth from any starting camera state — this is different from `CameraFocusRig`'s fix (exact snap + eased distance only) because `SelectionTracker` never has an "arrival" check to break, so continuous eased-target-lag is purely cosmetic here (and desirable), whereas in `CameraFocusRig` the same lag was a functional bug (see above).
- **Entering system view also starts distant, not close-up**: `SolarSystemScene`'s default camera position was `[0, 420, 560]` (distance ~700) — since this is the *only* starting camera for that Canvas regardless of how you arrive (breadcrumb, interstellar fly-in, or zooming out of a planet view), the system used to appear already fairly zoomed-in/spread-out the moment you entered it, inconsistent with the "basically a dot" exit feel. Pushed the default start out to `[0, 6300, 8400]` (distance ~10500, same viewing angle, ~15x farther) so the whole system reads as a small distant cluster on entry and the player zooms in deliberately — symmetric with the exit experience. Bumped the Canvas `far` clipping plane from `8000` to `40000` and `Stars` radius/depth from `2000`/`400` to `40000`/`8000` to match (the far plane was actually already stale/too-small relative to the `32000` `MAX_DISTANCE` set in the previous pass — worth double-checking `far` against `MAX_DISTANCE` any time either changes, since a too-small far plane silently clips geometry with no error).
